# Findings

What Xcrew's choices rest on. Measured in October 2026 on one Mac (macOS 26, Xcode 27.1, MobileBuildMCP 2.7.1) against a large modular Tuist app; versions move, so treat numbers as that snapshot. `xcrew doctor` checks the parts that can change under you.

## The two servers

| | Xcode MCP | MobileBuildMCP |
| --- | --- | --- |
| Ships with | Xcode 27 (`xcrun mcpbridge`) | Homebrew, from Sentry (formerly XcodeBuildMCP) |
| Builds through | Xcode itself, in Xcode's DerivedData | `xcodebuild`, in its own DerivedData |
| Knows | The open project: navigator, active scheme, real build settings | Whatever you point it at, through session-default profiles |
| Unique strengths | Per-file diagnostics, SwiftUI previews with variants, code snippets in a module, Organizer crash and performance logs, string catalogs, physical devices | Test filtering, coverage reports, simulator control and environment, UI automation by accessibility tree, LLDB |
| Settings | None of its own; Xcode decides | `.mobilebuildmcp/config.yaml`: tool groups, profiles, debugger backend |

They overlap on build, test and run. Xcrew sends those to MobileBuildMCP because its DerivedData never collides with Xcode's, its profiles survive restarts, and it filters tests. The Xcode MCP keeps what only it can do.

## Behaviours that shaped xcrew

- **The Xcode MCP works with Xcode closed.** After `sudo xcrun mcp-server enable`, the server runs headless. Each agent is approved once, through a dialog Xcode raises on that agent's first call; `xcrun mcp-server status` lists approved agents. A headless Xcode runs no Xcode app the process list shows (a field report, October 30, 2026: the doctor's `xcode/open`, a check since removed, said "Xcode isn't open" while it served); which Xcode it serves through isn't read, so it isn't compared with the builds'.
- **The Xcode MCP's file tools take project-navigator paths, not disk paths.** A disk path fails with "File not found in project structure".
- **`XcodeWrite` re-saves the whole project file.** Creating one file rewrote over a thousand lines of a generated `.pbxproj` in Xcode's newer format. Projects with synchronized folders, and generated projects, pick up files written to disk anyway, so the guard costs nothing.
- **Previews, snippets and diagnostics follow the active scheme.** "Active scheme does not build this file" means switching scheme, which also changes the person's Xcode window.
- **Macro plugins die after an in-place rewrite.** The kernel caches a Mach-O file's code signature and doesn't flush that cache when the file is rewritten in place, so the next launch is killed; Apple's guidance is to replace such a file rather than overwrite it ([Apple Developer Forums](https://developer.apple.com/forums/thread/130313)). **The trigger is the macro copy phase older Tuist versions generate.** Up to Tuist 4.202, for each macro target, Tuist generates a Run Script phase that copies the macOS-built plugin into the products folder of a non-macOS destination (`Debug-iphonesimulator/`) with `cp -f`, which writes into the existing file and keeps its inode. Reproduced directly: with a copy of a plugin running, as the compiler and the indexer keep them, `cp -f`-ing a new build over it makes every later launch of that path exit with SIGKILL, while a copy-and-rename over it runs again. Seen with Tuist 4.202.8. Tuist 4.203.0 removed the phase ([tuist#11825](https://github.com/tuist/tuist/pull/11825): "the macro executable copy build phase has been removed"), so projects generated with 4.203 or later don't have this trigger; upgrading Tuist and regenerating is the fix. It hits the regular build and the indexer's (`Index.noindex/Build/Products`) alike; a dead indexer copy breaks macro expansion in the editor without any failing build. Xcode's own linking doesn't trigger it: a plain Swift macro package rebuilt three times in Xcode 27.1 got a new inode each time and never died. The build reports "produced malformed response". Copying the bytes beside the plugin and renaming the copy over it revives it, and Xcrew did that automatically up to 0.6.10. It dropped the repair in 0.7.0: finding a dead plugin meant launching every plugin in DerivedData to probe it, and Tuist 4.203 removed the cause. The doctor named projects generated with the old phase for a while; that check is gone too. The same message also comes from other causes, such as a toolchain mismatch or stale prebuilt macros.
- **SourceKit can't read Xcode projects.** Claude Code's Swift language server reads settings only from a Swift package, a compilation database or a build server. Without a `Package.swift` it checks each file alone against the macOS SDK, so `import UIKit` and every first-party module show as errors. The Xcode MCP's `XcodeRefreshCodeIssuesInFile` uses the real settings.
- **The XcodeBuildMCP → MobileBuildMCP rename (2.7.1) has no fallback.** The binary, the `MOBILEBUILDMCP_*` variables and the config folder (`.mobilebuildmcp/`) all changed; an old `.xcodebuildmcp/config.yaml` is ignored silently, leaving only the simulator tools. An old binary on `PATH`, from Homebrew or npm, can shadow the new one.
- **MobileBuildMCP reads its config from its working directory**, so the plugin starts it in the project root.
- **MobileBuildMCP's test list can leave out a skipped test.** In a run that also crashed and recorded an expected failure, its text counted `1 skipped` but listed no `⏭️` line for it, though xcodebuild's log and the result bundle both had it. So Xcrew reads skipped tests and their reasons from the result bundle's test list (`xcresulttool get test-results tests`), not from that text. A dropped passing test is reported as getsentry/MobileBuildMCP#563.
- **`test_sim` takes no scheme argument**; the scheme comes from the session defaults, and `-only-testing:` goes in `extraArgs`.
- **MobileBuildMCP's command line resolves simulator names on the newest installed iOS only**; the MCP server doesn't have this limit.
- **LLDB `expr` needs `debuggerBackend: lldb-cli`**; the default backend handles attach, stacks and breakpoints.
- **Coverage tools need an absolute `.xcresult` path**; `~` isn't expanded.
- **The `mobilebuildmcp://doctor` resource reports Sentry as enabled regardless.** That line reads only a legacy variable; the environment section below it is accurate.
- **Sosumi beats `DocumentationSearch` for documentation**: short results with links, WWDC sessions, and each API's minimum OS version. `DocumentationSearch` matches the installed SDK and works offline.
- **`IDEAllowUnauthenticatedAgents`** lets any unsigned process drive Xcode's tools; leave it off. Turning it off doesn't cut Claude Code off: on October 29, 2026 (Xcode 27.2 beta 3, 27B5038j; macOS 27.0; Claude Code 2.1.312; MobileBuildMCP 2.7.1), setting it to `NO` and restarting Xcode left every doctor check `ok`, `xcode-mcp/claude-approved` included. That check reads a status, so a working Xcode MCP call is the stronger proof. On that Mac the value was already `1` before Xcrew first ran, so something else set it; Xcode itself is the likely source (unverified).

## A run's subagent

A run a subagent started carries the subagent's description on the line above the prompt and on its row, cut after 40 characters (`KEPT`, `hooks/mod/agent.ts`). Claude Code's Agent tool asks for "a short (3-5 word) description of the task" (its input schema, Claude Code 2.1.316). Of the 265 descriptions Claude gave subagents across one long working session on this repository (October 31 to November 2, 2026, Claude Code 2.1.314 to 2.1.316), the longest was 39 characters and 6 words, the median 23 characters: each fits under 40 whole. The line above the prompt is cut again at the terminal's width, after the description.

## Build and test progress

Measured October 2026 (Xcode 27.1, MobileBuildMCP 2.7.1, Claude Code 2.1.312). The band's gauge is time against the usual duration because no exact count reaches a mod:

| Layer | Exact progress? | What it carries |
| --- | --- | --- |
| Apple's build system (swift-build) | Yes | `BUILD_PROGRESS_UPDATED` messages with `percentComplete` and a status line (`Sources/SWBProtocol/BuildOperationMessages.swift`). Xcode draws its progress from them |
| Xcode MCP | Yes | MCP progress notifications (`Building • 836 / 850`), which Claude Code draws under the tool call |
| xcodebuild's output, as MobileBuildMCP logs it | No | Task lines naming their module, written as the run goes; one total near the start, `Target dependency graph (35 targets)`. Test results arrive in a few batches as the parallel runners flush |
| xcodebuild's result stream (`-resultStreamPath`) | No | Task start and end events only: a sample package's build gave 160 of each, no percentage or total |
| MobileBuildMCP | No | Its parser reports stages (compiling, linking, testing) and counts tests before a run from the test sources, but only its command-line tool receives them; the MCP server sends no progress |
| Claude Code's mod API | No | The `ToolProgress` render site carries only the run-in-background hint, and `$.mcp.call` returns only a result |

Counting modules from the log was tried and dropped: xcodebuild starts work on nearly every module early (33 of 35 had a task a quarter of the way into a clean build) and prints no line when one finishes, so the count sat near its total for most of the build.

## MobileBuildMCP's upkeep

Measured 2026-10-28. MobileBuildMCP is most of what Xcrew sets up, so how it's kept up decides how much Xcrew can lean on it.

| Since July 2026 | |
| --- | --- |
| Commits a month | 70–77 in March and April; 47, 11, 27, 3, 8 from May to September; 2 in October so far |
| Releases | 2.7.0 (July 23) and 2.7.1 (September 23), after one or two a month before |
| Issues opened | 42: 20 open, 15 closed as not planned, 7 completed; 19 of the last 23 closures were by a bot |
| Pull requests | 25 merged, 24 closed unmerged, 13 open; 14 of the merged ones are by one maintainer |

Sentry acquired the project in February 2026, and activity peaked in the two months after; the slowdown began around June. Xcrew's two reports, getsentry/MobileBuildMCP#563 and #564, are open.

What follows from it now: Xcrew works around MobileBuildMCP's problems in the mod and the CLI (compacting results, reading counts from the summary) rather than waiting on fixes, and keeps the Xcode MCP as the second server.

If upkeep keeps falling, the options, cheapest first:

1. **Lean on the Xcode MCP** for builds and tests, with MobileBuildMCP kept for what only it does (simulator control, UI automation, LLDB).
2. **Fork MobileBuildMCP** (MIT) and carry the fixes Xcrew needs. Cost: keeping up with Xcode and simulator changes ourselves.
3. **A server of Xcrew's own**, in Swift beside the CLI, covering only build, test and run on a simulator, with results shaped for an agent from the start. Cost: the largest, and it duplicates a working tool.

When to revisit: a new Xcode or iOS release that MobileBuildMCP hasn't followed within a few weeks, a bug that blocks builds or tests with no fix upstream, or #563 and #564 closed unanswered.

## Test reports from the two servers

Measured 2026-10-28 on a modular app's 961-test target (959 passing, 2 expected failures), with one assertion failure, one thrown error, one crash and one skipped test added on purpose, run on parallel simulator clones.

| | MobileBuildMCP alone | Xcode MCP (`RunAllTests`) | MobileBuildMCP with Xcrew |
| --- | --- | --- | --- |
| A failing run's result | Text listing every test, ~80 K characters, cut by Claude Code | JSON, ~20 K characters: up to 100 results, the rest in a file | ~1 K characters: failures, skipped tests, the summary |
| A passing run's result | JSON, ~122 K characters, saved to a file and read back with `jq` | JSON | ~1 K characters, the per-test list pointed to |
| Failure location | None (xcodebuild logs none for tests on parallel clones) | `file:line` as a project-navigator path | The file's absolute path and line, from the result bundle |
| Crash | Test and closure | "Test crashed with signal trap" | Test and closure, the exception, the crashed thread's top frames |
| Skipped test | Counted | Named | Named, with its reason |
| Expected failures | Left out of the counts | Counted | Named in a note with the true total |
| A filter matching nothing | `SUCCEEDED` with 0/0/0 | An explicit error | `SUCCEEDED`, flagged in the band and in a note to Claude |

A passing MobileBuildMCP test run hands Claude Code text, not JSON: `✅ 1 test passed, 0 failed, 0 skipped (⏱️ 4.4s)`, its JSON only in `structuredContent`, which the mod isn't handed (*MobileBuildMCP's CLI and its MCP results*). A failing run's line names the same counts in another order, `❌ 2 tests failed, 1 passed, 1 skipped`, so each count is read by its label. Seen in MobileBuildMCP 2.7.1's text (the test bed's `field/coverage.txt` and `captures/raw/`, October 30 and 31, 2026): the singular `✅ 1 test passed` only. No capture holds a plural passing line yet. Until then xcrew read counts from the `❌` line alone, so a passing run's outcome said no "N passed" and the next run's "testing N of M" had no M.

MobileBuildMCP's text writes a test run's counts only when it has some: `hasTestCounts = event.totalTests !== void 0 && event.totalTests > 0` (MobileBuildMCP 2.7.1, `utils/renderers/event-formatting.js:404`, read October 31, 2026), and `✅ Test succeeded.` otherwise. That covers a filter matching nothing (the test bed's `field/empty-filter.txt`) and a run whose counts MobileBuildMCP couldn't read, as when its own `xcresulttool` read of the bundle times out (`timeout: 1e4`, 10 s, `utils/xcresult-test-failures.js:33`). So the text can't tell them apart, and xcrew asks the result bundle: `totalTestCount` 0 is no tests ran, with a note saying the bundle counts 0; more is a pass with that count; with no summary to read, it stays a pass with no count. xcrew's own summary read has no limit of its own and runs to its end (*No budgets*).

**Discovered tests.** A test result lists the tests a filter selected, as `Discovered N test(s):` with up to six names, whatever the run's outcome: `createTestDiscoveryProgress` returns it whenever `tests.discovered` has a total above 0, and the result adds it right after its header (MobileBuildMCP 2.7.1, `utils/renderers/domain-result-text.js:1477-1488` and `:1926-1930`, formatted by `utils/renderers/event-formatting.js:419-430`, read November 2, 2026). The JSON holds the same as `data.tests.discovered`. A field report of October 31, 2026 (xcrew 0.11.0, a large modular app) had a UI test run filtered to one class come back `SUCCEEDED` with 0/0/0, its one test discovered and selected, under a test plan of three configurations: the filter matched, and none executed. So a run of no tests that lists discovered tests says so, naming the plan of several configurations its scheme runs by default. Without the list nothing tells the causes apart: in runs on the test bed (October 31, 2026, MobileBuildMCP 2.7.1, Xcode 27.2), a test plan that skips the test, a plan that leaves its target out, and a test compiled out with `#if` each came back 0/0/0 with no `Discovered` list, as a filter matching nothing does. So that note names them all and claims none.

As runners they differ the other way. MobileBuildMCP runs `xcodebuild` on its own, so it leaves the person's Xcode window, its scheme and its DerivedData alone; pins the simulator its profiles name; takes any `-only-testing` or `-skip-testing` filter; and adds coverage, simulator control, UI automation and LLDB. The Xcode MCP switches the IDE's active scheme to run, uses the scheme's own destination, and has no coverage. So Xcrew keeps MobileBuildMCP for builds and tests and makes its reports the smallest of the three, and the Xcode MCP stays the fallback runner in *MobileBuildMCP's upkeep* above, at the cost of those runner features.

A passing run's result reaches Xcrew only through the notice Claude Code puts in its place. The [MCP docs](https://code.claude.com/docs/en/mcp#mcp-output-limits-and-warnings) say only that it "replaces it in the conversation with a message that names the file path", and that "the file goes in the session's `tool-results` directory". So `Report.savedPath` finds the file by that path, an existing file in a `tool-results` folder named in a short text, and not by the wording. The docs put the saving point at 50,000 characters for a text result (October 2026); `Report.noticeLimit` reads a text as a notice up to 10,000, a margin for the saved JSON's schema the notice names. On October 29, 2026, Claude Code 2.1.312's executable carried one template for it, as source text: `Error: result (… characters) exceeds maximum allowed tokens. Output has been saved to ${path}.` followed by a newline and `Format: ${format}`. The weekly canary fills in that template from the newest Claude Code and checks that `xcrew report` still reads the saved result back (`scripts/saved-notice.sh`). A new wording, or a template the executable no longer carries as text, opens an issue.

A field report of October 31, 2026 (xcrew 0.11.0, a large modular app) had a test run moved to the background whose saved result was 119,619 characters, 118,324 of them its 354 build warnings, and it had no per-test list, so xcrew left it as it came. A saved result now has its warning list counted and pointed to in the saved file as well; its errors, failures, counts and artifacts stay, and the notes name the warnings in lines the branch changed. The mod puts the shorter result in the notification's place, as for a call answered in the foreground. A saved file that can't be read, or isn't MobileBuildMCP's JSON, leaves the result as it came. Any other saved result xcrew edits, its warnings collapsed or cut to those in changed lines, or an error line left out, comes back in the notice's place only once it's under the 50,000 characters at which Claude Code saves a text result, counted in UTF-16 units as JavaScript counts a string (`Report.savedFrom`). The docs give JSON no point of its own, so it shares that one, and a compacted result is held to it too, as its errors and failures, never left out, can run long. A test run's text whose bulk is its per-test timing, not its warnings, stays saved. Two limits: the docs (read November 2, 2026) also save a result past a token limit, 25,000 by default or `MAX_MCP_OUTPUT_TOKENS`, and give no characters per token, so a lower limit set by hand can let a shortened result under 50,000 characters back past it; and a result that stays saved keeps none of xcrew's edits to its text, which reach Claude only as its notes and the failures read.
- **The coverage runtime's own error isn't the run's.** A MobileBuildMCP test run whose app or tests can't write `default.profraw` lists `LLVM Profile Error: Failed to write file "default.profraw": Operation not permitted` among its errors (the hand-kept `mobileTestsBuildFailed` fixture, MobileBuildMCP 2.7.1; a field report of October 30, 2026 saw it on a large app too). The run goes on without that profile, so xcrew reads that write failure, and only it, as no error of the run's: it is left out of the failures listed and the errors `why` reads.

**A failing run's failed tests are its bundle's.** With a result bundle `xcresulttool` can read, a failing test run's failed tests come from the bundle's test list: each once, with its first failure's message as MobileBuildMCP words it (its first line, without XCTest's `failed - `) and its place from that failure's `sourceLocation`. The text is read for them only without a list, and for the run's other failures, the build's and the process's, which the bundle doesn't hold. The bundle lists tests by plan, target and suite, not in the order they failed, so the failures keep the text's order with the bundle's content, and a failed test the text leaves out comes after; the summary names the run's first failing test, or the bundle's first when the text names none. A test the text lists as failed that the bundle counts as passed, skipped or an expected failure in every entry under that name, as passed when a retry passed it, is no failure. Any other stays a failure, with the text's message and place: no result under that name, or `Failed` or `unknown`, the schema's others, in any entry, as one test bundle's killed run beside another's pass of the same name (xcresulttool schema 0.5.0, Xcode 27.2, read November 3, 2026), is no sign it passed. No capture has these shapes: their tests compose a test with no result and one recorded `unknown` from the retry capture, and one recorded both passed and `unknown` from a test list written out; that one is no failure cleared and no test passed, so the ledger doesn't turn it green. A test the bundle records `Failed` under the text's name is always among its failures, so a note never names one. A note names each with what the bundle records, a nested suite's test read only by the name the text gives it. Checked on the test bed's raw captures (November 3, 2026), against what the report gave from the text alone: a crashed test is a failure the bundle words as the text does (`Crash: xctest at …`), with no place; an expected failure and a known issue are no failure; a test a retry passed is none; Swift Testing through a test plan's configurations (`shapes-configurations`) lists no failure in its text in a shape the report reads, and the bundle gives it; a failure the text didn't place gets the bundle's place; a parallel run's failure on one of its clones is one failure (`parallel`, test bed v0.8.25). A crash the bundle files under `System Failures` (*A crash under System Failures*) is named after the test its message names, as the text's line is, so it's listed once, not again as `xctest (<pid>) encountered an error`, with the test bundle it was filed in. A message that names its test without an `in`, `Crash: xctest at Suite.test()`, is read the same; one whose last frame is no test taking no arguments, as `Crash: xctest at Model.load(from:)`, is no test's failure: the text's line stays, once, as one of the run's other failures. These shapes have no capture, and their tests compose them from the 27.2 one. A test in a nested suite, which the bundle names from its outermost suite and the text from its own, is matched by the end of the bundle's name when only one ends that way; no capture holds a nested suite yet.

**The test list is parsed once a report.** A report asks a run's test list (`xcresulttool get test-results tests`) up to nine questions: its failed, repeated, skipped, passed and expected-failure tests, each failure's target, and each test's runs. It's fetched once, and is now parsed once too (`TestList`), where each question parsed it again. Measured on November 3, 2026 (M1 Max, macOS 27.2, a release build, a synthetic list of 5,000 tests in 50 suites, each run three times, every fiftieth failing once, 10 rounds of the nine questions): 1,044 ms at the median with a parse each, 336 ms with one. What's left is the one parse and each question's own walk of the nodes.

## How Foundation sees a project's folders

Where Apple's docs are silent, the project search rests on these probes, taken on October 29, 2026 on macOS 27.0.1 with APFS, case-insensitive. Each is pinned by a test in `Tests/XcrewCoreTests/ProjectTests.swift`, so a platform change shows up red.

| Question | Docs | What came back |
| --- | --- | --- |
| Does listing a folder by URL follow a symlink to it? | `contentsOfDirectory(at:…)`: "does not traverse symbolic links" | It throws for a URL that is a symlink to a folder; `contentsOfDirectory(atPath:)` follows it. The search starts from the resolved root |
| Does `resolvingSymlinksInPath()` resolve the `/System/Volumes/Data` firmlink and letter case? | Silent beyond symlinks | Yes: a symlink to the home folder, `/System/Volumes/Data/Users/x` and `/USERS/X` all became `/Users/x`. `canonicalPathKey` alone leaves a final symlink unresolved |
| Is the volume case-insensitive? | `volumeSupportsCaseSensitiveNamesKey` | `false` here. Manifest names match without regard to case only where the volume says so |
| What is standard input: a file, a pipe or a device? | Silent | `FileManager.attributesOfItem(atPath: "/dev/fd/0")` reports `NSFileTypeRegular` for a file, `NSFileTypeUnknown` for a pipe and `NSFileTypeCharacterSpecial` for `/dev/null`; `/dev/stdin` itself reads as a symbolic link. A file is read to its end at once, since waiting on it for more input never ends |
| Which folders are packages? | `isPackageKey`: a package by its extension or by its own flag | True for `.xcodeproj`, `.xcworkspace`, `.app`, `.bundle`, `.playground`, `.xcdatamodeld`; false for `.xcassets`, `.framework`, `.xcframework`, `.lproj`, `.docc`, `.xctestplan` and dotted folders such as `MyApp.iOS`. The search skips a package or an `.xc…` folder, and enters the rest |

## The simulator setup picks

The session briefing names the simulators booted now. `simctl help list` documents the `booted` search term as "a simple case-insensitive contains check against the item's description", so a shut-down device whose name holds the word is listed too, and the briefing reads each device's `state`. On October 29, 2026 (macOS 27.0.1, Xcode 27.2 beta 3, CoreSimulator already running), `xcrun simctl list devices booted -j` took 0.12 to 0.14 s over six runs, and the session-start hook went from 0.02 s to 0.17 to 0.19 s with the service check below. A cold CoreSimulator wasn't measured. The briefing's `simctl` runs to its end (*No budgets*). It asks only while `com.apple.CoreSimulator.CoreSimulatorService` runs (`pgrep -x`, about 0.02 s): no simulator is booted without it, and `xcrun` would start it, or on a Mac without the developer tools offer to install them.

With Xcode 27.2 beta 3 on October 29, 2026, the iPhone Duo came on a runtime of its own. `simctl list runtimes` names it `com.apple.CoreSimulator.SimRuntime.iOS-27-2-iPhone19-4` and gives its `version` as 27.2, the same as the plain `iOS-27-2` runtime. Read from the identifier, it looked newer than 27.2, so setup picked the Duo. Setup now takes each runtime's version from `simctl list runtimes`, and falls back to the identifier's leading numbers only.

The Duo has two displays, and MobileBuildMCP 2.7.1's `screenshot` takes no display, so it fails there. `simctl` documents no display count. The device type's CoreSimulator profile, at its `bundlePath` from `simctl list devicetypes` plus `Contents/Resources/capabilities.plist`, lists its displays, and the built-in ones are powered on by default (`powerState` 1). That's `LCD` and `LCD-1` on the Duo, and `LCD` alone on the iPhone 17; `TVOut`, `Wireless` and `Resizable` are off. Setup never defaults to a device type with more than one, and the doctor warns about a configured one. The `displays` list is new with Xcode 27: on CI's `macos-26` runner (Xcode 26.x, the same day) a plain iPhone's profile had none, `plutil -extract` printed nothing, and no device type counts as two-display there, which is right, since those Xcodes ship no such device. A display without `powerState` counts as off, so the check fails open: a profile that drops the key would let a two-display device through. A test reads a plain iPhone's installed profile wherever it lists displays, so a change to that shape turns it red.
- **What the setup form offers** (`xcrew setup --choices`):
  - Only installed iOS simulators, each name once with its newest runtime, the two-display ones marked. The field report of October 30, 2026 had setup asked for simulators the Mac didn't have.
  - Only shared schemes, as for setup's unit-test scheme. A scheme's roles come from its build entries built for running and its test entries, by their targets' product types: an `application` it builds, `bundle.unit-test` and `bundle.ui-testing` bundles it tests. On the test bed's `field` fixture (v0.8.5), App's scheme builds the app and runs unit and UI tests, and each other module's runs its own unit tests.
  - Each scheme counts the unit-test and UI-test targets it runs by default, by the same product types, each target once: those its test action lists, and those of the test plan it marks `default = "YES"`, as the schemes Xcode wrote for the test bed's captures do. Apple's "Organizing tests to improve feedback" (read through Sosumi, November 2, 2026): "You must choose one test plan as the default plan for the scheme; Xcode uses this plan to run tests when none is explicitly specified." A scheme with no plan marked counts its first. Its app is the one its `LaunchAction`'s `BuildableProductRunnable` names when it also builds that app for running, else the first app it builds for running: a gallery scheme builds several apps and launches one, and a module's scheme can launch the host app it doesn't build. A field report of October 31, 2026 (a large modular app) had the form name a gallery app as its workspace scheme's app.
  - The picks are setup's own: the one scheme that builds an app, or the one named after its app; that scheme for UI tests when it runs them, else the only scheme that does; `TestSchemes.choose` for unit tests; `defaultIPhone`. The bundle ID is the app target's `PRODUCT_BUNDLE_IDENTIFIER`, when every configuration sets the same literal one.
- **Xcode 27's simulator app is DeviceHub.** Xcode 27.2.0 on macOS 27.2 (seen October 30, 2026; a test pins it against the installed Xcode 27 or later) ships `Contents/Applications/DeviceHub.app` and has no `Contents/Developer/Applications/Simulator.app`, so `open -a Simulator` fails. MobileBuildMCP 2.7.1 opens DeviceHub first and falls back to Simulator (`build/utils/focus-policy.js`). The session briefing says so when the selected Xcode has DeviceHub and no Xcode in the applications folder has Simulator.app, read from the bundles, not their versions.

## How mcs marks a project

mcs records each project it set up in `<project>/.claude/.mcs-project`, a JSON file that `mcs sync` writes, with the packs it configured under `configuredPacks` (mcs's `docs/architecture.md`, *Project State*, and `Sources/mcs/Core/ProjectState.swift`, read on October 29, 2026). ## How the plugin directory reads a plugin

## How a marketplace install picks its code

On October 29, 2026 (Claude Code 2.1.312), a fresh install from the marketplace recorded `version` `0.8.1` and `gitCommitSha` `5b646cc` in `installed_plugins.json`. That commit was five past the `v0.8.1` tag. With `"source": "./"`, the plugin came from the marketplace's own clone of the default branch, and [Host and maintain a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md) says updates follow `version` alone: "Users get a new copy only when the plugin's computed version differs from the one they have." So two `0.8.1` installs could run different code.

The entry now names the release tag (`"ref": "v<version>"` on a `github` source), which the same page documents: "`ref` names a branch or tag and `sha` names a commit for a `github`, `url`, or `git-subdir` source." Only the plugin's code follows the ref. The catalog, `marketplace.json`, is still read from the default branch, since only "`#<ref>` on the add command" changes that, so `claude plugin marketplace add breferrari/xcrew` works as before.

The ref moves in a pull request of its own, after the tag is pushed and the release workflow has published it. If the release pull request moved it instead, the catalog would name a tag that doesn't exist yet from the merge until the push, and installs would fail meanwhile. It would also still name the tag if the workflow refused it. Pinning a `sha` doesn't help either, since the squash merge makes the release commit and its hash isn't known before. A release branch added with `#release` would avoid the gap, but every existing user would have to add the marketplace again. So a test allows the ref to be this version or the previous release, and only a version the changelog has released. Since October 29, 2026, the entry names the `stable` branch instead, which the release workflow moves; see *Installs that follow a branch* below.

The first release through this flow, 0.8.2 on October 29, 2026, was checked without touching anyone's install: `CLAUDE_CONFIG_DIR=$(mktemp -d) claude plugin marketplace add breferrari/xcrew`, then `claude plugin install xcrew@breferrari --scope user` with the same variable. The temporary `plugins/installed_plugins.json` recorded `version` `0.8.2` and `gitCommitSha` `1273068`, the tag's commit, while `main` had moved on to the install pull request (`da128b3`).

## Xcode's scheme selection

Read in MobileBuildMCP 2.7.1's source (Homebrew, `libexec/build/`) on October 30, 2026; macOS 27.2, Xcode 27.2.

- **Only under Xcode.** `server/bootstrap.js:95-97` returns before any of this unless `runningUnderXcode`. `utils/xcode-process.js:2-6` sets that when the server or a process above it is named `Xcode`, or its command contains `Contents/MacOS/Xcode` or `com.apple.dt.Xcode`. `utils/process-tree.js:1-61` walks the `ppid` chain with `ps -o pid=,ppid=,comm=,args=` and splits each line on spaces, so the name is `comm`'s first word. With a column after it, `ps` cuts `comm` to 16 characters (`/Applications/Xc`), so the path past them counts only through `args`. In a terminal session, Xcode's selection never reaches the server, whatever Xcode has selected.
- **At the start, whatever the config says.** `bootstrap.js:104-150` reads the state once (`readXcodeIdeState`) and calls `sessionStore.setDefaults`, which writes into the profile active then (`utils/session-store.js:46-47`). `disableXcodeAutoSync` gates only what follows.
- **Then each change, unless `disableXcodeAutoSync`.** `bootstrap.js:151-169` starts `utils/xcode-state-watcher.js`, which on a change writes a new, non-empty scheme over the profile active then (`processFileChange`, lines 59-88). The flag comes from the config file, else `MOBILEBUILDMCP_DISABLE_XCODE_AUTO_SYNC` in the server's environment (`utils/config-store.js:113, 201-213, 332-337`). xcrew reads the file only.
- **Which file.** `utils/xcode-state-reader.js:51-143`: `<workspace>/xcuserdata/<whoami>.xcuserdatad/UserInterfaceState.xcuserstate`, or `<project>.xcodeproj/project.xcworkspace/…`. The configured `workspacePath`, else `projectPath`, comes first when its file is there. Otherwise every `*.xcworkspace` and `*.xcodeproj` folder `find` reaches within six levels of the server's folder, a project's own inner workspace left out, workspaces first, and the newest file by `stat -f %m`. The parent search stops at the workspace root (`utils/workspace-identity.js:4-14`), the config's project folder, which is the server's own.
- **How it's read.** `utils/nskeyedarchiver-parser.js:34-84`, through `bplist-parser`, so only a binary property list: an `NSKeyedArchiver` archive, the first dictionary in `$objects` whose `NS.keys` refers to the string `ActiveScheme`, that key's value, and its `IDENameString`. Foundation reads the archive's references as `CFKeyedArchiverUID`, which `PropertyListDecoder` refuses ("found a uid instead") and whose index only `PropertyListSerialization`, through a pointer, gives. So xcrew reads the binary format itself (`BinaryPropertyList`).
- **What Xcode wrote.** Xcode 27.2, opening the test bed's `field/Field.xcworkspace` with no state, wrote a 9 KB binary state whose `ActiveScheme` named `App` and whose `ActiveRunDestination` named `dvtdevice-iphonesimulator:<udid>`. The fixture is that file with its paths, ids and window frame replaced.

- **The global defaults' name.** The session tools report the profile in use as `(default)` when it's the global one (`mcp/tools/session-management/session-format-helpers.js:2-4`, `formatProfileLabel(null)`), which `session_use_defaults_profile` with `global: true` selects. It reads the config's `sessionDefaults`.

So a run that names no scheme is kept under the scheme its own log names: MobileBuildMCP's run log opens with xcodebuild's `Command line invocation:`, whose `-scheme` is what was built (the test bed's raw captures' logs, MobileBuildMCP 2.7.1, November 2, 2026; `RunLog.scheme`). A run whose log never appears is timed and shown, and kept nowhere. Until the log appears, the mod works out a scheme only to pick the usual time and test total, in order: the session's own listing of its defaults (`session_show_defaults`), newer than anything before it; Xcode's selection, under Xcode, read once when the session starts and again until the server is found, written over the profile active as it was read; the profile chosen in the session (`project --profiles --profile <name>`, `(default)` for the global defaults); and the config's active profile. That guess can differ from the server's, which is why it no longer keys anything:

- A selection changed in Xcode after the server's start, which the server follows unless `disableXcodeAutoSync`, isn't read.
- With `disableXcodeAutoSync`, a selection changed between the server's start and the mod's first answer, as while the CLI first builds, is taken as the start's.
- MobileBuildMCP drops every container `find` lists when `find` exits non-zero, as on an unreadable folder within six levels (`xcode-state-reader.js:79`); xcrew's walk skips that folder and goes on.
- A restarted server reads the selection again at its start; the mod reads it once, and keeps it across a cleared conversation as the server does.

**How much of the log is read for the scheme.** The invocation is xcodebuild's own first output, not a line MobileBuildMCP writes. MobileBuildMCP 2.7.1 builds the command as `xcodebuild`, `-workspace` or `-project` and its path, then `-scheme` (`utils/build-utils.js:57`), and adds the extra arguments last (`:125-126`), each `-only-testing:` among them naming one selected test (`utils/simulator-test-execution.js`). A test run's second phase, `test-without-building`, names no scheme (`utils/test-common.js:108-118`), so the first heading, the build for testing's, is the one read. So `-scheme` sits within the heading, the indent, xcodebuild's path and the container's path, each path at most `PATH_MAX`, 1,024 bytes on macOS (`sys/syslimits.h`): about 2.1 KB plus the scheme's name, however many tests a run selects. ## What an install copies

A marketplace install copies the plugin's whole folder, which for xcrew is the repository. The plugin docs offer no ignore file and no include or exclude list ("Create a marketplace", "Plugin sources", read October 29, 2026). The one way to narrow a copy is the plugin's `source`: a relative path or a `git-subdir` copies only that folder. That is why the test bed lives in its own repository, [xcrew-testbed](https://github.com/breferrari/xcrew-testbed), and why the README's images now live in [xcrew-assets](https://github.com/breferrari/xcrew-assets), pinned by commit.

The images were 3.3 MB of a 5.4 MB install. Moving the plugin into a folder with a `git-subdir` source would have narrowed the copy further, to 1.3 MB on October 30, 2026, but the directory checks a plugin in a subfolder more strictly ("Plugin pre-submission checklist", read that day). A hook or server command that names a variable other than `${CLAUDE_PLUGIN_ROOT}` "Blocks when the plugin folder is a subfolder of the repository", which xcrew's `${CLAUDE_PROJECT_DIR}` argument may trip. Scripts that use shell variables or call other files of the plugin are held for a reviewer on every version. The checklist's remedy is to "keep the plugin at the root of its own repository", so the plugin stayed at the root and the images moved out. Measured that day in throwaway configs: the cached copy went from 5,440 KB to 2,152 KB, and Claude Code's shallow marketplace clone from 8,772 KB to 3,120 KB.

A plugin with a top-level `bin/` doesn't install on claude.ai or in Cowork ("claude.ai and Cowork don't install a plugin that has this directory", plugin reference, *Standard layout*). xcrew needs a Mac with Xcode, so those apps aren't its reach, and its `bin/` stays.

A byte ceiling on what an install copies ran in CI from 0.9.0 to 0.9.1. It was dropped on October 30, 2026, because it fired on ordinary growth in code and tests and caught nothing.

The marketplace reference says a git source's `ref` is "a branch or tag", and the plugin loading reference says an installed plugin's version comes from "the `version` field in the plugin's manifest" first, which `claude plugin update` compares to decide whether to update. ## Disk space

Read October 30, 2026, on macOS 27.2 with Xcode 27.2, MobileBuildMCP 2.7.1 and xcodes 1.6.2; every command read-only, nothing deleted, no simulator booted. `xcrew space` reads what follows, only when asked: the doctor scans no disk.

It walks every file: 1.15 s for 28 workspaces and 316 MB here. `--older-than` takes days, `30d`. Without `--classes`, a dry run covers logs, result bundles, test products and transients, not DerivedData; `--delete` needs explicit `--classes` and `--confirm delete-mobilebuildmcp-storage`, and DerivedData only when named (`purge.js`, `purge-ui.js`). So `space` names each workspace's classes that exist and the report marks `cleanupEligible` (`locks` never is), and no command over `--scope all`, which reaches every project's workspaces.
- **Units, builds running, and what to purge first.** A field report of October 31, 2026 (xcrew 0.11.0, a large modular app, APFS) read xcrew's 126.2 GB against `du -sh`'s 119G as a disagreement: xcrew counts decimal GB, as Finder does, and `du -h` binary GiB, so 126.2 GB is 117.5 GiB. Readings taken while a 9.5-minute build wrote DerivedData showed 150 GB, DerivedData 62.3 GB, and 24.2 GB after it. Test products took 95 of the 119 GiB: 105 `.xctestproducts` bundles of 4.6 GB each, one per `test_sim`, on-disk and apparent sizes equal. So `xcrew space` says its unit first, gives its total in both, and says when an xcodebuild writes to a workspace's DerivedData (its `-derivedDataPath` below the workspace's folder) as it reads. The dry run it suggests leaves DerivedData out, test products first, counted in bundles: the next test run makes a bundle again, while DerivedData costs a cold build (8 minutes there) and gets a dry run of its own. The doctor gave one line of it until 0.12.0; now `xcrew space` alone reports storage, when asked.
- **One workspace's report is much cheaper.** `--scope workspace --workspace-key <key>` reports that workspace alone, and a key with no workspace answers an empty `workspaces` and totals of 0 (MobileBuildMCP 2.7.1). A field report of November 1, 2026 (a large modular app, about 190 GB across a Mac's workspaces) timed the `--scope all` report at 21.7 s and its own project's workspace at 0.8 s. So the doctor's storage check asked for each of the project's checkouts by key, until it left the doctor: `xcrew space`, which sizes the whole Mac once, gives this project's total against its budget from the same report.
- **A workspace's family is its root's folder name alone** (`build/utils/workspace-identity.js`), so a project's Claude Code worktrees, at `.claude/worktrees/<name>`, are each a family of their own, and another project of the same folder name shares one. xcrew finds a project's workspaces by key instead, from each checkout `git worktree list` names.
- **MobileBuildMCP records no workspace's root**; its registry record holds only process ids. A build log's `-workspace` or `-project` names the container, and the key's hash, the root's SHA-256, confirms which folder above it is the root. Here that confirmed 7 roots (4 gone), one log's container didn't hash to its key, and 20 workspaces had no log naming one. Only a confirmed root is said to be gone, and only when the folder above it is there: a root on a volume not mounted is missing too, yet not gone.
- **What a purge keeps.** It never removes a workspace's folder, and it keeps a log written in the last hour and one named with a live helper's pid (`WORKSPACE_FILESYSTEM_LIFECYCLE_MIN_VISIBLE_MS`, `utils/workspace-filesystem-lifecycle.js:22` and `:129-140`, MobileBuildMCP 2.7.1, read November 2, 2026), with the state its servers keep. A gone project's workspace holding only what a purge keeps is now counted on one line with no command; a purge an hour on takes its logs. xcrew suggests no delete inside another tool's storage: a recent log may be a running process's.
- **It sweeps on its own**, when a workspace's server starts: logs, result bundles and test products older than 3 days (`build/utils/workspace-filesystem-lifecycle.js`). It never sweeps DerivedData, nor a workspace whose server doesn't start again, as a removed worktree's.
- **Xcode's own parts are cheaper to read.** `xcrun simctl runtime list -j` gives each runtime's `sizeBytes` and, not always, `lastUsedAt`: the runtime a two-display device ran on had none, its device holding 2.2 GB, so a missing `lastUsedAt` isn't "never used". `xcrun simctl list devices -j` gives each device's `dataPathSize` (0.1 s, against `du`'s 1.6 s). Spotlight's `kMDItemPhysicalSize` sizes an Xcode at once (`du`: 4.4 s); it has none for a plain folder. Each of Xcode's DerivedData folders names its workspace in `info.plist` (`WorkspacePath`), so one whose workspace is gone is known. `simctl runtime delete` takes `--notUsedSinceDays`, `--unusable`, `--outdated` and `--dry-run` (`xcrun simctl help runtime`).

## A call moved to the background

Claude Code's mod types (2.1.314, read October 30, 2026) say nothing of a `tool.call` result being a handle rather than the call's outcome: `ToolCallResult` has `result`, `text`, `context`, `ref`, `isReadOnly` and `isError`, and the one render site about it is `ToolProgress` kind `background_hint`, the "(ctrl+b to run in background)" pill, which shows the offer, not whether it was taken. The mods reference is silent too. What they do document is the end: a background task's notification arrives as a turn whose `prompt.submit` origin is `{ kind: 'task-notification' }`, whose text a hook may rewrite and to which it may attach `context`, and its `UserMessage` row carries `task`, with `id`, `toolUseId` ("Which call started the task: its tool_use_id, when the notification carries it"), `status` (`completed`, `failed`, `killed`, or another word) and `durationMs`.

So it was measured. On October 30, 2026 (Claude Code 2.1.314, interactive sessions through a pty, no simulator), a scratch plugin's stdio MCP tool answered after 150 s, past the 120 s at which Claude Code moves a call to the background, and a scratch mod logged `tool.call`, `prompt.submit` and the notification row:

- **The handle.** `tool.call`'s `next` resolves with `MCP tool "…" is still running after 120s. It was moved to the background as task k4q5tm9v2 and keeps running; you'll receive a notification with the result when it completes. …`, with the call's `tool_use_id` on the event. It's the only place that ties the task to the call. The executable carries two more wordings, for a call moved so that a message can reach Claude, and for a server-side task, whose own id comes first; all three say "It was moved to the background as task ${id}".
- **The notification.** `prompt.submit` fires with that origin, no `isMeta`, no `turnId` and no context. Its text is `<task-notification>`, `<task-id>`, `<status>` and `<summary>` lines, then the result between a `<result>` line and a `</result>` line. A 2,000-character result came whole; a 50,036-character one came as Claude Code's saved-result notice (*A passing run's result*, above). The executable builds an MCP task's body from a template, `` `\n<result>\n${…}\n</result>` ``, and names the tags in constants (`"task-notification"`, `"task-id"`, `"status"`). The notification names no `tool_use_id`.
- **The row.** `ui.render` on `UserMessage` with that origin carried `task: { id, status }` only, drawn twice: no `toolUseId` and no `durationMs`. xcrew 0.9.3 matched the row by `toolUseId`, so its line that a call ended in the background never showed in a real session; only its tests, which supplied one, saw it.

- **A failed task (November 2, 2026).** MobileBuildMCP answers a failing test run with an error result, so Claude Code marks its task `failed`. A field run (xcrew 0.13.0, Claude Code 2.1.316, a large modular app) had two such notifications come back as "Task failed: 🧪 Test … Warnings (380): ⚠ …", the server's whole text, which xcrew left as it came, reading a failed task from its log alone. The executable holds a "Task failed: " string beside its MCP task code; which tag carries the text, the summary after that prefix or a `<result>` block, isn't measured yet. So both are read, and the text is reported on as an error result, its failures named and recorded as in the foreground. The capture that settles the shape waits on a research login.

So the mod reads an outcome only from a result that is the server's: `xcrew report` marks a build or test result as unread when it isn't an error and holds nothing in its server's own forms, no JSON shape the server uses and not one line of the kinds MobileBuildMCP writes. A test runs every captured result of both servers, passing and failing, through that rule, and none reads as unread. Of an unread result, `xcrew report` reads the task's id from the handle's words (`backgroundTask`). The mod shows the call as neither passed nor failed, records nothing, and keeps it by that id. When a notification comes whose text holds a waiting call's id, the mod hands the notification to `xcrew report --notification`, which reads `<status>` and, for a completed task, the result, or for a failed one the server's error result, and reports on that as on a foreground answer; its shorter result takes the result's place in the notification Claude reads, and its notes are attached as context. The run ends at the notification, timed by the server's own duration, or else from the call, and counted among the runs that ended meanwhile. A result that can't be read, or a task that was killed, leaves the run's MobileBuildMCP log: `xcrew report --log` reads the log's last xcodebuild verdict (`** BUILD SUCCEEDED **`, `** TEST EXECUTE FAILED **`; for a test run, only its tests' own, and none for a run interrupted) and, for a test run, each failing test from the result bundle the log names, through `xcresulttool`. The ledger takes a run's tests only from a result or a bundle the CLI read, never from the log's verdict alone. When nothing says how the run ended, the row's line says the task ended in the background, or was killed or failed, now found by the row's `id`. The fixtures in `BackgroundTaskTests` are the probe's texts, and the weekly canary fills in the handle's template from the newest Claude Code and checks the notification's tags and body template (`scripts/background-texts.sh`). A render hook only reads its row: the line is shown just after the drawing, through `$.clock.after`, since a state write made while drawing didn't reach the band in `claude plugin test`.

The run itself goes on, though: a field report of October 31, 2026 (xcrew 0.11.0) had builds and test runs longer than 120 s drop off the line above the prompt for minutes. So a call whose handle names a task, of a server whose log the mod follows, stays on the band, going and marked as in the background, and the mod goes on reading its log through `xcrew phase`. It ends on the first signal that settles it: the notification, which records it as above, or the log's xcodebuild verdict (`outcome`), which shows on the band while the notification still records the run, once. A run is followed until one of those ends it, however quiet its log and however many calls wait for their notification: one left before then would never be read as a run (*No budgets*). Where the band doesn't draw, the status line keeps counting the same way. Claude Code moves a call at 120 s, so a log that appears only after the move, as after a long step before xcodebuild, is one the call never saw. So the notification's report, when the call never saw its log, is given the tool and the call's start, and finds the run's log: the first `<tool>_` log of this session's servers opened at or after the call's start, by the time MobileBuildMCP names each log with when it opens it (*Which log is the run's*), compared in whole milliseconds as both are written. The newest log written since, as the band reads while a run goes, could be a later call's by the time the notification is read. The run is then read from its log and recorded under the scheme it names. A run in the foreground that ends before the ticker has read its log's scheme, as a fast build does, is asked about the same way at its end. Two cases still take another run's log: two calls of one tool started in one session before either's log appears, the band's limit too, and a run that never opened a log, as one whose server stopped first, which takes the next call's.

The scratch mod's first version didn't load: its hooks handed `$` to a helper declared inside `register`, and Claude Code refused the module with "… $ is followed nowhere else; $ is always spelled $.noun.event(...) at the call site, on is always on("<event>", hook) …". That's the rule Claude Code's docs state, and why every `$` call is in `register.ts`, in functions declared at its top level ([architecture](architecture.md#why-registerts-holds-every--call)).

## Which log is the run's

While a MobileBuildMCP build or test runs, the band reads its log. MobileBuildMCP 2.7.1's source, read on October 29, 2026 from its Homebrew install's `build/`, says where that log is. `utils/workspace-identity.js` names a project's workspace folder with `workspaceKeyForRoot`: the root's folder name with every run of characters other than letters, digits, `.`, `_` and `-` made one `-`, then a `-`, then the first 12 hex digits of the SHA-256 of the root path. The root is the folder above `.mobilebuildmcp/` when a config was found, else the real path of the server's working folder. `utils/xcodebuild-log-capture.js` names each log `<tool>_<timestamp>_pid<server pid>_<suffix>.log` as it opens it, the timestamp the time then as ISO 8601 in UTC with `:` and `.` made `-` (`utils/log-naming.js`, read November 2, 2026). Matching workspace folders by name prefix let two checkouts of folders with one name, and two sessions in one checkout, read each other's logs. Foundation's `resolvingSymlinksInPath()` drops a leading `/private` (`/private/var/…` comes back as `/var/…`), while Node's `realpath`, which MobileBuildMCP uses, keeps it; `canonicalPathKey` matches Node. A test whose expected key came from the code's own path call couldn't see the difference; one whose expected key comes from `/bin/realpath` and `shasum` did. So `RunLog` computes the exact key, under both the root as given and its real path, and keeps only the logs of the MobileBuildMCP servers under this session's Claude Code. A test runs the installed `workspaceKeyForRoot` with the Node runtime MobileBuildMCP ships, wherever it's installed (this Mac, the weekly canary), so a change upstream shows up red.

## When a generated project is stale

After Claude edits a manifest, the generated project changes only when the generator runs again. File times can't say whether that happened. On October 29, 2026, with Tuist 4.214.0 on the test bed's Tuist fixture, `tuist generate` kept the workspace's and `project.pbxproj`'s modification times in two cases:
- after `touch Project.swift`;
- after an edit that produced the same project.

Tuist writes only files whose content changes. Comparing a manifest's time with the project's would therefore read "stale" forever after a generate that changed nothing. So the mod marks the project from what it sees this session: an edit to a manifest marks it, and a `tuist generate` or `xcodegen generate` that succeeds clears the mark. A test runs a generate on a copy of the fixture wherever Tuist is installed, so a Tuist that starts rewriting unchanged files shows up red.

An edit undone leaves nothing to generate: a field report hit a build refused after a manifest edit was reverted to a clean diff. So the mark keeps each edited file's SHA-256 from before its first edit since the last generate (`xcrew project --hash`), and before refusing a build the mod reads them again: a mark whose files all have their hash back is dropped, and the build runs. Content, not times, as above. A hash that couldn't be read, then or now, leaves the edit standing, and so does an edit a build was already refused for: the person may have generated from it in their own terminal since, so undoing it leaves that project stale. The build it holds back then says so: a field tester read the source to learn why a build was refused again after an undo (October 31, 2026, xcrew 0.11.0). It's held back once, and the next goes through, as after any refusal. An undo made with Edit or Write is read as it's made, so its note says the next build needs no generate; one the edit tools don't see, as a `git checkout`, is found by the next build. An edit made while a build reads the hashes keeps its mark.

The mod can tell a failed generate only by the Bash result's `isError`. The engine's types say it's set when the tool "reported an error", without naming an exit status. In this repository's session transcripts (Claude Code 2.1.312, October 29, 2026), every Bash command that exited non-zero is stored as an error result whose text starts `Exit code 1`. The mod's tests stand on that. A shell reports a pipe's or a list's last command, so a generate piped into `tail` or followed by `; echo` would look like a success even when it failed. Such a command clears nothing, and the build is refused once more.

A person may regenerate in their own terminal, which the mod can't see. So the mark refuses one build and then lets the next one through, with a line saying why.

The stale guard holds back a run tool unless its name says it only launches. `RunProject` builds before it launches. Whether the Xcode MCP's `DeviceInteractionInstallAndRun` builds first is unverified, so it is held back by that rule too; the next session where the Xcode MCP connects confirms it from `tools/list`, with `RunSomeTests`.

## XcodeGen's included specs

XcodeGen reads every spec its spec includes, so an edit to one marks the project stale like an edit to `project.yml`. Read on October 30, 2026 from XcodeGen's `Docs/ProjectSpec.md` and, where it is silent, `Sources/ProjectSpec/SpecFile.swift` on master:

- "Include can either be a list of includes or a single include. An include can be provided via a string (the path) or an object". The object has `path`, `relativePaths` and `enable`, both flags defaulting to true.
- "Included specs can also include other specs and so on." The loader reads each file once.
- Where an include resolves isn't in the docs. The source keeps a base folder and a relative folder for each spec and reads an include at the base joined with its path. A top-level include therefore resolves from the root spec's folder. A nested one resolves from the folder of the spec that includes it, or, with `relativePaths: false`, from that spec's base.
- An absolute include path stands alone: XcodeGen joins paths with PathKit, whose `+` returns an absolute right-hand side unchanged.
- The loader walks includes depth first, in the order written, and keeps the first spec it reads at each path. A spec reached twice therefore resolves its own includes from its first route.
- A flag is read by `resolveBoolean`: `dictionary[key] as? Bool ?? (dictionary[key] as? NSString)?.boolValue`.
  - Yams, XcodeGen's YAML library, resolves `yes`, `true` and `on`, their negatives, and each in lower, capitalized or upper case, to booleans (its `Resolver.default`, read October 30, 2026).
  - Any other text goes through `NSString.boolValue`.
  - A number resolves to neither a Bool nor a String, so the flag keeps its default, true.
- A disabled include is never read (`.filter(\.enable)` comes before the file is loaded). `${NAME}` in a spec, an include's path among them, expands from the variables the loader is given: the environment.

xcrew reads only the top-level `include` key, in those documented forms, with no YAML dependency. It resolves includes the same way. An include whose path holds a variable, or whose `enable` isn't a literal, is left out, since it depends on the environment at generate time. JSON specs are out of scope: detection doesn't find a `project.json`, and the mod doesn't ask about a JSON spec a YAML spec includes. The CLI tests pin each case. Since a spec can include another by any name, the mod asks the CLI about every YAML file edited in a project XcodeGen generates, and about none elsewhere: a CI workflow's edit in any other project started two CLI calls for nothing.

## The red-to-green ledger

The mod gives Claude the ledger through a tool of its own, registered with `$.tool.register`. The engine's types (Claude Code 2.1.312, read October 30, 2026) say:
- the model "calls it as `mcp__<plugin>__<name>`", hence `mcp__xcrew__ledger`, which the hook answering it matches by that literal;
- of `isDeferred`: "Left out, the engine's rule places it: behind ToolSearch, as it places an MCP server's tool." The mod leaves it out, so the tool costs a session nothing until Claude searches for it.

A ledger is kept per branch, in `$.store`, under the project's real root and the branch `git symbolic-ref` names. With HEAD detached it is kept under the commit, which a later checkout of a branch never meets again: no attempt is made to carry it over.

A run turns a red green when its own results list the test as passed:
- **What lists it.** For MobileBuildMCP, the result bundle's test list (`xcresulttool get test-results tests`), each `Test Case` whose `result` is `Passed`, filed under the test bundle that is its target. A test of the same id failing in another target isn't a pass, as MobileBuildMCP counts it. For the Xcode MCP, its `results` whose `state` is `Passed`, which name no target; it gives at most 100 inline (*Test reports from the two servers*), so a red past them stays red after a passing `RunAllTests`.
- **Where.** The same scheme as the run it fails in now, whichever tool ran it (`RunAllTests` then `RunSomeTests`, `test_sim` then `test_device`), and the target the report named for it when both name one. The scheme stays in the rule because a target isn't always named: the Xcode MCP gives none, and a red recorded without one would otherwise turn green on a test of the same name in another scheme's target. Any selection counts, `-skip-testing:` and the Xcode MCP's `RunSomeTests` included, since the list says what ran. A Swift Testing name is the same test with its `()` or without.
- **A failing run counts as well**, for the reds its list holds as passed.
- **Why not the selection.** The ledger first inferred a pass from the run's scope, then from a selection that reaches the test. A field report of October 31, 2026 (xcrew 0.11.0, a large modular app) had a test deleted from its file turned green by a run of its class that never ran it, and the evidence block wrote "red → green" for it. A selection says what could run, the list what did.
- **A red the newest run left out.** A red test that a run of its scheme left out, as one deleted or renamed since it failed, is said to be "not in the newest run of its scope", in the ledger and the evidence block alike, with when that run was. Only a run that would have run it counts: its scheme's whole suite, by any tool, or a selection holding the red run's own, of a scheme known by name, and with none of its tests left out on purpose (`-skip-testing:`, `-testPlan`, a configuration) nor repeated: those runs share the scope of one that ran them all. Only a whole list of passed tests counts too, from the run's result bundle, with at least one test in it: the Xcode MCP's list stops at 100 results, and a failed build passes none. A later run that runs it, failed, passed or repeated, ends that. The entry's age isn't refreshed by it, so a test that's gone leaves the ledger once no run has failed it for as long as the history is kept. A test the run skipped, or never reached because an earlier one crashed it, reads the same.
- **Greens from before.** A green carries `listed` once a run's list gave it. A stored green without it was inferred from a selection by an older xcrew, so its entry is left out: a false green already in a ledger doesn't reach the evidence block, and its red, long over, doesn't come back as one. Reading those entries as still red, as xcrew 0.12.0 to 0.13.1 did, listed every test a branch had fixed under "Still red" after an upgrade, until a run listed it again. The ledger rebuilds from new runs. An entry marked flaky keeps its red and its mark: 0.11.0 turned a flaky test green after one clean repeated run, short of the passes it needs now. Those versions also saved the entries they read as red, so a ledger a test run wrote since holds them as plain reds, which nothing tells apart from a real one; they go once no run has written them for as long as the history is kept.
- **Cost.** The list costs one `xcresulttool` call on a run that read none, so the mod asks for it (`xcrew report --passed`) only while the branch's ledger holds a red with no green. It reads the ledger while the run goes, after the writes queued before it, and again at the run's end only when another run wrote it meanwhile, so a run longer than that read adds nothing between its end and its result.

A run whose report the CLI couldn't read is left out, since its outcome would be a guess. Writes happen after the run's result goes back to Claude, one after another, and reading the ledger waits for them.

## What a generator writes

An edit to a file a generator writes is lost on its next generate, so the mod asks the person before one runs. Read October 30, 2026:
- **Tuist** (*Synthesized files*): it will "synthesize the content of those files and write them into the `Derived` directory". That directory is "relative to the directory containing the project that defines them", and the docs say to "add the `Derived` directory to the `.gitignore` file of your project". Tuist also writes the `.xcodeproj` and `.xcworkspace`.
- **XcodeGen** (*ProjectSpec*): "Plists are created on disk on every generation of the project", at a target's `info` or `entitlements` path. The `.xcodeproj` is named by the spec's `name`.

What sits beside a bundle or a `Derived` folder decides whose it is, so each app in a repository is guarded and a dependency's checked-in project isn't:
- An XcodeGen spec writes only the `.xcodeproj` its `name` names, so a workspace CocoaPods wrote beside it isn't XcodeGen's.
- A Tuist manifest, by detection's rule (its ProjectDescription import below the root), writes the project, the workspace and `Derived`.

A Write that creates a file is matched through its nearest existing folder, since `/var` is `/private/var` on disk.

XcodeGen's `info` and `entitlements` paths aren't counted yet, because reading them needs the spec's target keys. The mod's first look matches bundle names as the CLI does, case and all. It reads the whole path, so a project checked out below a folder named `Derived` asks the CLI on every edit, which answers no.

`$.ui.ask`, per the engine's types (Claude Code 2.1.312), "Rejects when dismissed, and in a `-p` run (no one to ask)". Either way the mod refuses the call with the reason, as it did before it asked. The types name no error that tells a dismissal from a failure to show the dialog, so any rejection refuses. A typed answer refuses too, carrying the person's words, rather than the mod reading their intent.

## The project card

The card used to reach Claude with a conversation's first message, through a mod's `prompt.context` hook. The engine's types (Claude Code 2.1.312, read October 30, 2026) said the event fires once per conversation and its answer stands until a compaction or `/clear` reads it again.

### Prompt hooks a plugin can't count on

On a Team organisation, Claude Code's own security plugin, `cc-plugin-sec-default`, seats itself outermost and passes over a user plugin's `prompt.context`, `prompt.section` and `prompt.attachment` hooks and its `classic.*` ones. The person sees a line saying the hook was skipped, and the card never reaches Claude. Reported upstream as anthropics/claude-code#103626 (a `classic.UserPromptSubmit` hook bypassed on every session's first prompt), #104236 (`classic.Stop`, `StopFailure` and `SessionStart` passed over on Team organisations) and #102653 (`prompt.attachment` hooks no longer running since 2.1.299), all open on October 30, 2026. The engine's native events (`tool.call`, `session.start`, `prompt.submit`, `command.run`, `ui.render`) and the command hooks in `hooks.json` still run. So the mod registers none of the passed-over hooks, which a ManifestTest pins.

### How it reaches Claude now

The mod saves the card after each run and at session start: `xcrew card --save` keeps one entry per folder (as the file system spells it) and branch (its name, `commit <sha>`, or nothing outside git, as the ledger files it), dated by its newest and its oldest line, one file per folder and branch under `~/Library/Caches/xcrew/cards/`, so two sessions saving at once each keep their own, each written whole through a file renamed over it. `xcrew hook session-start`, the plugin's command hook, prints the entry for the folder and the branch checked out now at the end of its briefing, with how old its data is ("as of the run 2 h ago"), unless its oldest line is older than the history is kept, as the mod dropped each line by its own age (`HISTORY_KEPT_MS`, the same number of days on both sides, paired by a test). Claude Code's hooks reference (read October 30, 2026) lists `SessionStart`'s sources as `startup`, `resume`, `clear`, `compact` and `fork`, and a hook with no matcher fires for all of them, so the card comes back after a `/clear` or a compaction as it did before. The hook's `additionalContext` is capped at 10,000 characters; the briefing is about 3,300 and the card at most 800.

The store is the plugin's, across every project, and a run scope (`test_sim · App`) doesn't name one. So each run records the session's folder (`$.session.cwd()`), and the card shows only scopes last run in this folder. Scopes from before that record stay out until they run again. The card is capped in lines and characters, with longer lists counted as "+N more".

At a session's start the mod drops the times, counts and ledgers of a folder that no longer exists, as a worktree removed since: a field report filed November 2, 2026 had them kept for one removed two days earlier. The mod touches no files, so it asks `xcrew gone` with each folder the store names, once, as a read nobody waits on (*Failed reads*). When the CLI doesn't answer, every folder keeps what it stored, so a failed call never empties the store. Only a folder the system says doesn't exist counts (`FileManager.attributesOfItem` failing with `fileReadNoSuchFile`), so one macOS's privacy rules refuse to show, or any other failure to look, keeps its data. A folder under `/Volumes/<name>` counts only while that volume is mounted, read from `FileManager.mountedVolumeURLs`, which Apple documents as returning the mounted volumes: a drive taken out leaves its checkouts unreachable, not gone, and a ledger can't be rebuilt by running again. On macOS 27.2 (November 2, 2026) the list held `/`, the `/System/Volumes/…` volumes and `/Volumes/Recovery`, each volume by its folder, which a test pins for `/`. A path that reaches the startup volume through `/Volumes/Macintosh HD` isn't in the list by that name, so it is kept too. Any folder outside `/Volumes` is on the startup volume, always mounted. A missing folder counts only while its parent folder exists too: `git worktree remove` takes the worktree's folder and leaves the one holding it, while a share unmounted from outside `/Volumes`, as under `/net`, takes its folders' parents with it. A share whose empty mount point stays behind can't be told from a removed folder, and a tree deleted whole keeps its data until the two-week rule takes it.

## Affected tests

`xcrew affected` reads which target owns each changed file, and which targets depend on which, from the project file. Saying "skip this" wrongly lets broken code look green, so whatever the reading doesn't model runs everything, with the reason named.

- **The JSON format** (`project.xcproj`): the keys come from Apple's `xcode-project-format` package (its *Schema Overview* and its `Schema` sources, read October 30, 2026):
  - a file's and a folder's `target-membership`;
  - a folder's `membership-exceptions`, each with a `target` and `inclusions` or `exclusions`;
  - a target's `dependencies` and `test-host-target`.

  In the overview's words, "Groups do not participate in targets", while a folder's discovered content "is implicitly added to the folder's targets". The test bed's files carry trailing commas, so they're read with `JSONSerialization`'s `.json5Allowed`.
- **`project.pbxproj`** is undocumented. It's read as an OpenStep property list through `PropertyListDecoder`, whose docs don't name the formats it reads; the test bed's classic forms pin that it reads this one. `PropertyListSerialization` would take a format pointer, which strict memory safety refuses. Files join targets through PBXBuildFile and build phases, with paths resolved through groups and `sourceTree`. Folders join through PBXFileSystemSynchronizedRootGroup, a test bundle's host through the product its `TEST_HOST` names.
- **Running everything:**
  - a change inside a project or workspace bundle (the project file, schemes);
  - an `.xcconfig`, `.xctestplan`, `Package.swift` or `Package.resolved`;
  - a manifest the generator reads;
  - a file no target owns, or one an exception set moves;
  - a linked product, test host or dependency that no project the workspace reads builds;
  - a project file that can't be read.
- **Dependents count at any depth.** A change to a framework selects the tests of every target that builds on it, however far up.
- **What counts as depending:**
  - an explicit dependency;
  - a test bundle's host;
  - linking another target's product (a `BUILT_PRODUCTS_DIR` reference in a build phase, a `<PRODUCTS>` file's `target-membership`), which Xcode follows implicitly.

  Targets of the same name in two projects keep every dependency. Across projects, a modular Tuist app connects its modules by product alone: App links `Feature.framework`, which only Feature's project builds, with no dependency entry (the test bed's `modular/tuist-modules`, Tuist 4.214.0, October 30, 2026). So each project records what it builds and what it links without building, and the workspace resolves those links across every project it reads. A dependency entry can also point into another project, through a proxy whose container is that project's file; it resolves by the target its `remoteInfo` names. A linked product or a proxied target that no project here builds runs everything.
- **Ownership:** a file inside a bundle the project lists whole (an asset catalog, a data model) is the bundle's. An exception set naming a folder covers the files under it.
- **The change:** git lists it with `--no-renames`, so a moved file's old owner counts too, and with `-z` and `--no-relative`, so every name comes back as written. With no `origin/HEAD` (a clone sets it, a push doesn't), `origin/main` and then `origin/master` are tried. With a remote but none of them, everything runs. Only with no remote at all is the working tree the change.
- **The loop budget:** the routing rules name `affected`, but a line read at session start fades in an edit-and-test loop. So when one scope's last few full runs all fall within a short window and add up to minutes of testing, the result of the run that crossed it names `affected` again, once; then the count starts again. The numbers are `LOOP_RUNS`, `LOOP_WINDOW_MS` and `LOOP_TESTING_MS` in `hooks/mod/loop.ts`, as of October 30, 2026: 3 runs, 30 minutes and 3 minutes. A suite that takes 20 s never crosses them, however often it runs. A full run is one the CLI read, that ran tests, and that ran its scheme's whole suite once: a `-only-testing:` selection, a `-skip-testing:` run, a repeat, or a run narrowed or retried by another option `man xcodebuild` names (`-only-test-configuration`, `-skip-test-configuration`, `-testPlan`, `-retry-tests-on-failure`, `-run-tests-until-failure`) doesn't count, nor does a test build that failed. The count is the session's, so another session on the branch doesn't add to it. The note never blocks a run, and it says the tool is behind ToolSearch. For the Xcode MCP the note names `affected` alone: its own selection tool isn't confirmed yet. A scheme chosen by a MobileBuildMCP profile rather than the call's `scheme` shares the bare `test_sim` scope, as the run's duration history does.
- **What Claude reads, count first.** The field report of October 30, 2026 had a branch touch a core module of a large modular app: 334 test targets, about 20 KB of text, UI and unit mixed. So the answer gives the count first, then the targets by what runs them. A UI test bundle, `bundle.ui-testing` in both formats' product type, drives the app on a simulator, while a unit test bundle runs in its host. A kind's targets are named with their `-only-testing:` arguments up to `ARGUMENTS_UP_TO` of them (`hooks/mod/affected.ts`); past that, `NAMED_UP_TO` are named, the rest counted, and the whole list is `xcrew affected`'s JSON, from Claude's Bash or a `!` command. A scheme that tests more than `NAMED_UP_TO` of them is counted rather than listed.
- **Which schemes, and how many.** A field report of October 31, 2026 (xcrew 0.11.0, the same app) had a core change select 334 of about 350 test targets: the answer listed about 200 module schemes, about 14 KB, and never named the workspace scheme that tests everything, the one its CI runs. A narrow change of 8 targets got its six module schemes, which were right. So when the selection is more than half the suite's test targets, `xcrew affected` names the scheme that tests every selected target with the fewest targets beyond them, and nothing else; with no such scheme, it lists as for a narrower change. Otherwise it lists the schemes that test only selected targets, the first `NAMED_UP_TO` named and the rest counted, and for a selected target none of them tests, the scheme that tests it with the fewest more, as `\`S\` tests T with 1 more`, rather than saying none tests it.
- Paths are compared as the file system spells the project's folder, `.` and `..` resolved by their words. `standardizedFileURL` would drop `/private` from `/private/var` and miss.

## The module graph

`xcrew graph` reads the same project files as `affected`, and each target's Swift sources for their `import` lines.

- **The layers are the declared dependencies.** A project names its layers nowhere else that can be read without running something. Tuist metadata tags (`.metadata(tags: ["layer:…"])`): Tuist's docs suggest a `layer:` prefix but give tags no layer behaviour (*Metadata tags*, read October 30, 2026). On a copy of the test bed's `field` fixture with `layer:core` on Core (Tuist 4.214.0, Xcode 27.2), the tag appeared in `tuist graph -f json` under `metadata.tags`, and in no file `tuist generate` wrote. So reading tags means running Tuist. Tuist's *TMA* guide recommends a naming convention (`Feature`, `FeatureInterface`, `FeatureTesting`…), but nothing in a project says it's followed.
- **Each import is placed, not judged:**
  - declared: a direct dependency;
  - transitive-only: reachable only through other dependencies;
  - undeclared: not reachable;
  - upward: the imported module depends on the importer.

  Tuist's `tuist inspect dependencies` calls the transitive-only case an implicit dependency. On the fixture copy above, it reported `App implicitly depends on: Core` once App imported Core. Projects rely on transitive-only imports on purpose, so the graph states the class and nothing more.
- **Embedding isn't depending.** Tuist puts every framework below an app's dependencies into the app's *Embed Frameworks* phase, while it links only the ones the manifest names. In the test bed's `field` App, Feature is in Frameworks and Embed Frameworks, Core and Data in Embed Frameworks alone (test bed v0.8.5). The reading keeps how a target comes to build on each other one: named as a dependency, linked (*Frameworks*), copied in (*Copy Files*), or its test host (`TEST_HOST`). The graph counts one the target only copies as `embeds`, not as a dependency; one it also links, names or runs in is a dependency. `affected` follows every edge, since a change to an embedded framework reaches the app.
- **Module names.** Apple's build settings reference describes `PRODUCT_MODULE_NAME` as "Must be a valid identifier" and gives no default (read through Sosumi, October 30, 2026). `xcodebuild -showBuildSettings` derives it from `PRODUCT_NAME` (Xcode 27.2, the test bed's `forms/classic`):
  - `My-App 2.x` → `My_App_2_x`;
  - `2Fast` → `_Fast`: a leading digit is replaced, not prefixed;
  - `a+b` → `a_b`;
  - `Café_Ünï` unchanged.

  `ModuleGraph.identifier` follows that. A target's own `PRODUCT_MODULE_NAME` wins when every configuration gives the same literal value: `buildSettings` in `project.pbxproj`, and in the JSON format `build-settings`, where a configuration's value has a conditional key (`PRODUCT_MODULE_NAME[config=Debug]`; apple/xcode-project-format's `Target` and `BuildSetting`, read October 30, 2026). A value built from another setting is noted, and the product's name is used. An `.xcconfig` that renames a module isn't read.
- **Imports are read by their words**, by The Swift Programming Language's grammar (`attributes? import import-kind? import-path`) and SE-0409's access level before `import`, with comments and string literals skipped. An import inside `#if` is marked conditional, since the condition isn't evaluated.
- **A new file in a generated project belongs to no target** until the project is generated again: Tuist lists each source in the project file.
- **Names two targets share.** A library's product is `libCore.a`, and its module is `Core`. Two targets can build one module name, one per platform. An import of it is placed by whichever of them sits nearest the importer.
- **A Swift file a target only copies**, listed in its *Copy Bundle Resources* phase and not its *Compile Sources*, is no source of it: `graph` reads no import from it and `--owner` names no target that builds it. `affected` still counts it, since a changed resource changes the target's bundle.
- **Not read yet:** the JSON format's embed-only products. A member's `build-phase` (`App/frameworks`, `App/resources`) isn't read, so a `<PRODUCTS>` file a target is a member of counts as a dependency, and every file it's a member of counts as one it compiles. That waits on the review of Xcode 27.2's project format.

## Concurrency diagnostics

`xcrew concurrency` counts a build's Swift concurrency diagnostics by the compiler's own diagnostic group and by module, from the build's log.

- **The group is in the diagnostic.**
  - Since Swift 6.2 a grouped diagnostic ends with its group: `[#MutableGlobalVariable]`. A group under another is written parent first, `[#RegionIsolation::SendingRisksDataRace]`.
  - Errors carry it too.
  - Groups come from Swift's `include/swift/AST/DiagnosticGroups.def` (read October 31, 2026). It defines no concurrency parent. Its only links are `RegionIsolation` over `SendingRisksDataRace`, `SendingClosureRisksDataRace` and its `RegionIsolation*` groups, and `PerformanceHints` over its own.
  - Seen in the test bed's `concurrency` capture (v0.8.7, Xcode 27.2, MobileBuildMCP 2.7.1), in xcodebuild's log, MobileBuildMCP's result and the log it names.
- **Which groups are concurrency's: the docs of the Xcode that built it.**
  - The log names that Xcode, in the first path into its `Contents/Developer` folder. It may not be the selected Xcode, which is the fallback.
  - The default toolchain ships one doc per group, at `usr/share/doc/swift/diagnostics/<name>.md`.
    - Xcode 27.2 heads each `# <title> (<Group>)`. It has 76 docs, no `region-isolation-*` ones, and index pages whose heading names no group.
    - Swift 6.2, which Xcode 26 ships, heads each with its title alone (swiftlang/swift at `swift-6.2-RELEASE`, read October 31, 2026). The file's name, in PascalCase, gives the group. For every concurrency doc there that's the group's real name: `sendable-closure-captures` is `SendableClosureCaptures`.
    - So where some heading names its group, one that doesn't is an index page; where none does, the file names the group.
    - Xcode 26.0 (CI's oldest toolchain, October 31, 2026) ships two group docs, `AvailabilityUnrecognizedName` and `ImplementationOnlyDeprecated`, neither about concurrency. There the name words decide every group.
  - A group counts when its doc speaks of concurrency or data races, or its title names `Sendable` (`ExplicitSendable`, whose doc mentions neither), or when the words in its name say so: `sendable`, `sending`, `isolat`, `actor`, `concurren`, `datarace`, `globalvariable`.
    - A doc may say less than its name. Swift 6.2's `IsolatedConformances` doc speaks of neither concurrency nor data races; Xcode 27.2's speaks of data races. So the docs add groups and titles, but never take one away.
    - A body's `Sendable` isn't enough: `ImplicitStrongCapture`'s doc has one in an example's code and isn't about concurrency.
  - `InstalledGroupDocsTests` checks that the name words catch every group the installed docs call concurrency's, so the words alone are never weaker than the docs. CI's oldest toolchain, Xcode 26, found 6.2's headings this way, with no group in them.
  - The kinds the report gives are these groups, with their doc's title, and nothing of xcrew's own.
- **Not every concurrency diagnostic has a group.** In Xcode 27.2, "stored property 'box' of 'Sendable'-conforming struct 'Holder' has non-Sendable type 'Box'" carries none. A Swift diagnostic with no group is counted apart, never sorted by its text. A C or Objective-C file's warnings carry a flag (`[-Wdeprecated-declarations]`), not a group, and aren't counted.
- **`ActorIsolatedCall` is an error** even in the Swift 5 language mode with complete checking: "call to main actor-isolated instance method 'draw()' in a synchronous nonisolated context [#ActorIsolatedCall]". It stops the module's region analysis, so in the same module the `Sending*` warnings don't appear. That's why the capture's warning build leaves it out.
- **Once each.**
  - xcodebuild's log writes each warning two or four times. MobileBuildMCP's result lists it once, and its log repeats it as xcodebuild's does.
  - The report counts each (file, line, message, groups) once. On the capture that gives exactly MobileBuildMCP's list (`eachDiagnosticOnceIsMobileBuildMCPsList`).
- **The log, read in pieces.**
  - The report reads the run's own log, which holds every diagnostic; a server's result may be cut short.
  - It reads 1 MB at a time and splits lines on the newline byte, dropping a `\r` before it.
  - Only a line whose bytes hold `warning: ` or `error: ` is parsed, by hand. Task headers and the Xcode's path are found by bytes too. A sample showed `String.contains` and a `Regex` per line spending most of the time on grapheme boundaries.
  - On a 50 MB log (the capture's warnings log repeated, 220,000 lines, a release build, October 31, 2026), the report took 0.97 s and 73 MB at most. Per-line `contains` and `Regex` had taken 5 s.
  - A build that compiled only some files logs only theirs, and the report says so.
- **Module:**
  - The target the log's task header names, `SwiftCompile … (in target 'Kit' from project 'App')`, above the diagnostic. That covers a package's sources, which no project file lists.
  - Failing that, the target that owns the file, through the workspace reading `xcrew graph` uses, after the path is spelled as the file system does.
  - Else "not in a project".
- **Changed lines:** the lines *Warnings in changed lines* reads. `--changed` keeps only those.
- **The note after a build.**
  - After a MobileBuildMCP build or test whose log holds `ConcurrencyReport.noteAt` (10) concurrency diagnostics or more, Claude reads one note: how many, in how many modules, and that `xcrew concurrency` lists them. Nothing more, so the note runs no git.
  - MobileBuildMCP's result lists each diagnostic once (MobileBuildMCP 2.7.1, the test bed's `concurrency` capture, v0.8.7, October 31, 2026; pinned by `eachDiagnosticOnceIsMobileBuildMCPsList`). So a result listing fewer than 10 can't hold that many, and its log isn't read. A passing run that answers in JSON names its log in `artifacts.buildLogPath`.
  - The mod gives the note once per scheme a session, a build and a test run of one scheme being one. It's given again only when the count is at least `CONCURRENCY_RISE` (a quarter) above the highest it has given for that scheme (`hooks/mod/concurrency.ts`). A build that compiled only some files logs fewer, which is the log's doing, not the code's: a drop never gives it again, and doesn't lower the high mark. So 40, 12, 40, 50 gives it at 40 and at 50.
  - The Xcode MCP names no log, so it has no note.

## Flaky or real

Running a failing test again settles whether it's flaky. Read October 30, 2026:
- **`man xcodebuild`** (Xcode 27.2): `-test-iterations number` means "tests will run number times". `-retry-tests-on-failure` and `-run-tests-until-failure` cap that number, so a run stops at the first pass or the first failure. `-test-repetition-relaunch-enabled YES` gives each repetition "a new process".
- **Apple's *Diagnose unreliable code with test repetitions*** (WWDC21): fixed iterations repeat "regardless of the status" and are "great for understanding the reliability of your test suite", while retrying "can hide problems in the actual product". So the routing rules ask for `-test-iterations 5` with a relaunch, never the modes that stop early.
- **`xcresulttool get test-results tests --schema`** (schema 0.5.0): a test's runs are its `Repetition` children, each with its own `result`.

**MobileBuildMCP passes both flags through.** MobileBuildMCP 2.7.1's `utils/test-common.js` and `simulator-test-execution.js` send `extraArgs` that aren't selectors to both its build-for-testing and test-without-building phases. `utils/test-source.js` filters out only `-project`, `-scheme`, `-destination`, `-derivedDataPath`, `-configuration`, `-testProductsPath`, `-workspace`, `-xctestrun` and the action names. The man page doesn't say whether build-for-testing takes test options. Run on this Mac on the test bed's classic form, it took both and built, printing only "Running tests repeatedly 5 times."

**The verdict:** a test that failed some of its runs and passed others is flaky, whatever the count, since a minimum would hide the rarest flakes. Failing every run makes it a real failure. The ledger keeps a flaky test red, marked flaky, until repeated runs have passed it enough times in a row; one run passing it is no evidence. A test that failed 1 of 5 runs passes 5 in a row 0.8⁵ = 33% of the time, so one clean repeated run of 5 is weak evidence. Enough is the least `n` with `(1 − rate)ⁿ < 0.05`, `n ≥ ln 0.05 / ln(1 − rate)`: 6 after 2 of 5, 14 after 1 of 5, 59 after 1 of 20. Passes from repeated runs add up; a failure resets them and folds every run since the mark, the passes included, into the rate. A plain run's failure, or one a repeated run gives no verdict for, resets the passes too, but stays out of the rate: plain runs' passes aren't counted, so counting their failures alone would overstate it, and the mark would need fewer passes than it should. The rate is measured, so from few runs it can understate a rarer flake, and the ledger says so. `xcrew flaky` works the number out, and the mod keeps it.

The mod knows a repeated run by `-test-iterations` in its `extraArgs`, and only then has the report read the bundle's test list. The test bed's `captures/repetitions` pins the reading: a real run's `xcresulttool` answer for three tests run five times each, passing every run, failing every run, and failing every other run, made on the Mac and replayed, so nothing nondeterministic runs in CI.

## Warnings in changed lines

A large project builds with hundreds of warnings, and a few new ones among them go unseen. The report names the warnings that fall in lines the branch changed since its merge base with the default branch, uncommitted and untracked files included: the change `xcrew affected` reads, through `GitChanges`. No state is kept. An edit that only moves a line doesn't make its warning look new, and the answer is right on a branch's first build.

- **The lines:** `git diff -U0` (`git help diff`, read October 30, 2026: "Generate diffs with <n> lines of context") gives each hunk's header and nothing around it. The header follows the unified format, `@@ -l,s +l,s @@`: the new side's start and count, where a count of 0 adds no line and an omitted count means one. It's run with `--no-prefix`, `--no-renames`, `--no-relative` and `core.quotePath=false`, and only over the files with a warning: when none of them changed, it doesn't run. A header still writes a name with a space followed by a tab, and C-quotes one with a quote, a backslash or a control character; both are read back. Lines end at the `\n` byte, since a CRLF file's `\r\n` is one Swift Character. Its hunk lines are counted off from the header, since a removed `-- a` prints as `--- a`, like a file's header. An untracked file counts whole. Checked on macOS 27.0.1 with git 2.56.0 on APFS, October 30, 2026, and pinned by `gitGivesTheChangedLinesOfEveryKindOfName`: an absolute pathspec spelled `/private/var/...` selects the file from a repository opened as `/var/...`, and the space and quote shapes above are what came back.
- **The warnings:** MobileBuildMCP's `⚠` lines with the `/path:line` after each, read before repeats are collapsed, its JSON's `diagnostics.warnings`, and the Xcode MCP's build entries whose `classification` is `warning`. One listed again at the same place counts once, and the total counts those without a place too. A warning's path is compared as the file system spells it (`/private/var` for a temporary folder at `/var`), as the compiler writes it.
- **What Claude reads (November 2, 2026):** the result lists only the warnings in changed lines, and one line counts the rest, saying where the full list is: the result Claude Code saved for its size, else the run's build log the result names. In text it goes under `Warnings (N):`, each warning left out going with its location line; in JSON the kept ones stay in `diagnostics.warnings`, beside a `warningsLeftOut` line. A failed background run's notification is read the same way. Field shape: a backgrounded test run's result of 119,623 bytes held 118,324 of warnings (354), and two failed background runs came back with 368 and 380. No count decides it: a result lists a warning when it's Claude's to fix, the change's own, and leaves out what the change didn't touch. With no base to compare with, as outside git, every warning stays.
- **Its gap:** a warning the change causes in a line it didn't touch, such as each call site of an API it newly deprecated, isn't named. The note says which warnings are in changed lines, and never that a change added no warnings.

## Changed lines a test run ran

A test run that passes says nothing about the lines a change added that no test ran. When a MobileBuildMCP test run's result bundle has coverage, the report counts the lines the branch changed that can run, the ones the run ran, and names the rest, with the changed files the coverage doesn't hold. The change is the one *Warnings in changed lines* reads. The note speaks for this run alone: a run limited by `-only-testing` doesn't run a line another test would.

- **Whether there is coverage:** `xcresulttool get content-availability --path <bundle> --compact` answers `hasCoverage`, a field its schema requires (`xcresulttool get content-availability --schema`). Apple's Xcode 16.3 release notes added the command ("information about the available content in a .xcresult bundle, including code coverage"), so every Xcode xcrew supports has it. A bundle that says `false` asks nothing of `xccov`. One whose answer can't be read has its report read all the same, so a failing `xcresulttool` costs what it did before. On November 2, 2026 (macOS 27.2, Xcode 27.2, APFS), across the 39 MobileBuildMCP result bundles on one Mac, it agreed with `xccov` on every one: 17 said `false`, where `xccov` failed with "No coverage data in result bundle", and 22 said `true`, where it listed files. It answered in about 0.02 s, where any `xccov view` took 0.63–0.64 s, most of it `xccov`'s own start. A passing test run's `report`, timed with release builds (5 warm runs each), went from 0.68–0.72 s to 0.13 s on a bundle without coverage (the test bed's `shapes`), and from 1.30–1.33 s to 0.68–0.69 s on one with it (`swift-testing`), with the same output. MobileBuildMCP 2.7.1's `test_sim` doesn't turn it on: the scheme, its test plan or `-enableCodeCoverage YES` in `extraArgs` does, and it passes `extraArgs` through. The routing rules say how it's turned on, and that it slows a run.
- **The lines:** `xccov view --archive --file <path> --json` gives one file's lines (`man xccov`, read October 30, 2026: the archive "contains the raw execution counts for each file in the report"). The files are those the report below names: on November 2, 2026, the 22 bundles with coverage above listed the same files in `--archive --file-list` as in `--report`, so xcrew asks for the report alone and not the list too, one `xccov` start fewer. MobileBuildMCP's `get_file_coverage` reads it the same way. Its JSON isn't documented. Probed on macOS 27.0.1 with Xcode 27.2 (27B5038j) on APFS, a Swift package and the test bed's app tested with coverage on, it's `{"<path>": [{"line": 1, "isExecutable": false}, {"line": 4, "isExecutable": true, "executionCount": 1, "subranges": [...]}]}`. A line counts as run when its `executionCount` is above 0, whatever its subranges say. The test bed's `captures/coverage` keeps a real answer that tests replay, and the weekly canary checks the newest Xcode's against xcrew's reading (`scripts/coverage-shape.sh`).
- **The paths:** the report and the archive spell each file as the build was started: `/tmp/...` where the file system says `/private/tmp/...`. Both sides are compared as the file system spells them. Only the files named like a changed file are resolved, since an app's coverage can list thousands, and their line counts are asked of `xccov` a few at a time, within a budget: past it the note is dropped and the rest of the report stands.
- **Files outside the coverage:** a changed file is named when its kind (its extension) is one the coverage holds and the coverage doesn't hold it. Only files under the project count, and never a package's or Tuist's manifest, which the build reads and no test runs. A file `xccov` can't give counts for leaves no note, rather than a count it can't back. In the probe, a package's generated scheme gathered coverage for its test target and not its library, so this is common. In an Xcode project, a changed file that only test targets build, by the project's own targets (`WorkspaceGraph`, as `xcrew graph --owner` reads them), isn't named: a test target's own files are no code under test, so their being outside the coverage says nothing (a field run of November 2, 2026, xcrew 0.13.0, named a UI test target's file after a run of one module's tests). The project's targets are read only when there's a file to name and the coverage's budget hasn't passed, since the reading can't be stopped once started; its time on a large workspace isn't measured. A file an exception set may move, one no target lists (a local package's test file among them), and any file of a project whose targets can't be read (a plain Swift package's included) keeps its place.
- **Tests and targets the run didn't reach:** `xccov view --report --json` gives each target of the run's coverage, with its product (`buildProductPath`), how many of its lines can run (`executableLines`) and ran (`coveredLines`), and its files by `path`. Its JSON isn't documented. The test bed's field capture keeps an app's (`captures/field/coverage.report.json`, a run under `-only-testing:FeatureTests/ProbeTests/testPasses`, Xcode 27.2, October 30, 2026), where targets are named with their product's extension (`Feature.framework`, `FeatureTests.xctest`). The same day the canary's package gave one target, `ShapeTests`, named without it and holding only the test file, its library not in the coverage at all; its product, like the app's test bundle's, ran through `ShapeTests.xctest/`. The coverage holds a test bundle's own files beside the code they test, so a branch that changed a test had its lines counted as code. A file is now left out when every target holding it is a test bundle, told by its product, or one the run didn't reach: a target with lines that can run, none of which ran, as when a filter leaves its tests out. Such a target's changed files are said once, as "this test run ran nothing in Core", not line by line. A file of a reached target counts whether or not its own lines ran, so a file really left untested still shows. One odd target is skipped, not the whole report; without a report there is no note, since the report names the files. The weekly canary checks the newest Xcode's report through the same code (`scripts/coverage-shape.sh`).
- **A run of no tests:** ran none of the changed lines, which says nothing of them, so it has no coverage note, beside the note that it ran no tests.
- **The Xcode MCP:** its test results carry no result bundle path xcrew reads, so its runs have no note.

## Which Xcode

A Mac with several Xcodes builds every project with whichever `xcode-select` last chose. A project that pins its own builds with it, and a failed build whose errors another SDK or toolchain gives says when CI, or the Xcode that's open, uses another.

- **The pin is `.xcode-version`.** It's xcodes' published convention (`XCODE_VERSION.md`, read October 30, 2026): one version string, such as `16.4` or `14.0b6`, in a file beside the project or workspace. xcodes and fastlane read it. xcrew looks at the root and beside each Xcode container, and compares by the version's numbers, so `27.2b3` and `27.2.0` both name 27.2. Setup never writes one: a pin is the team's choice. A failed build's note suggests one only when several Xcodes are installed and CI names its own.
- **Applying it:** `man xcode-select` says `DEVELOPER_DIR` "overrides the active developer directory" for the process that has it. MobileBuildMCP 2.7.1 has no Xcode setting of its own (its source has none), and its `xcodebuild` and `simctl` inherit the server's environment. So `libexec/mobilebuildmcp-server` sets `DEVELOPER_DIR` to the pinned Xcode's developer folder before it starts the server.
  - It asks the CLI (`xcrew xcode --developer-dir`) only when a quick look finds an `.xcode-version`: the root, then three levels down, past hidden folders and those the project walk skips (`node_modules`, `Pods` and the like), whose pins are other projects'. It's looser than the CLI's rule, so a pin it finds that the CLI doesn't count costs one short call. The CLI checks the pin first and looks in the applications folder before Spotlight.
  - It asks only of a build that's there, through the shim's `--if-built`, and waits for its answer however long it takes, inside Claude Code's 30 s for a server's start (*No budgets*). A first build takes seconds and would hold up the server's start, so it never starts one.
  - On no answer, it starts the server as it would without a pin.
- **The record:** what the launcher did goes in xcrew's cache, below `launches` at the project's real path with a `.launch` suffix (so a project inside another has its own), as facts: `applied <developer folder>`, `no match`, `not built`, `timed out <seconds>` (the timer stopped the CLI, status 143) or `failed <status>`. `xcode/pin` reads it and words it. The launcher writes it and then becomes the server (`exec` keeps its process), so the running server's record is no older than its start, by `ps`'s `etime`: an older one is an earlier start's, and the server started before the pin. With no server serving the project, as from a terminal before a session, nothing has had the pin to apply yet, and `xcode/pin` says only that. A path in another letter case reaches the same record on a case-insensitive volume, and on a case-sensitive one it's another folder anyway. The doctor can't read the server's environment instead: on macOS 27.0.1, `ps -E` printed no environment even for a child of the same shell, so the record is the only witness.
- **The installed Xcodes:** the apps in `/Applications` and those Spotlight finds by `kMDItemCFBundleIdentifier == 'com.apple.dt.Xcode'`, each read from its `Info.plist` (`CFBundleShortVersionString`) and `version.plist` (`ProductBuildVersion`). On this Mac (October 30, 2026), Xcode 27.2 beta 3's version reads plain `27.2`, with only its build, `27B5038j`, telling it apart, and Xcodes.app shares the `Xcode` prefix. So a bundle counts by its identifier, not its name. Some past release builds also ended in a letter (15.0's was `15A240d`), so nothing is read as a beta by its build. When a beta and a release share a version, a pin without a `b<n>` prefers the app whose name doesn't say beta, one with it the app whose name does, and the first by path among equals, in the launcher's lookup and the doctor's alike.
- **The open Xcode:** the Xcode MCP works through the Xcode that's running, which no pin changes. xcrew finds it by its process (`ps -axo comm=` ends in `.app/Contents/MacOS/Xcode`), and a failed MobileBuildMCP build or test whose errors another toolchain gives says when it differs from MobileBuildMCP's (`XcodeFailureNotes`): two toolchains in one session. The doctor checked it ahead of time until it kept only what xcrew needs to run, as it did CI's Xcode, said now on the same failures. That process shape is `ps`'s full executable path, not yet seen here with Xcode open.
- **Where a mismatch shows:** which Xcode builds is the person's choice, and may be deliberate. So a pin no installed Xcode matches stays off `doctor --problems`, the line above the prompt's source, and shows in the full doctor at warn; a pin MobileBuildMCP started without, a launcher fault whose fix is a restart, still shows there. A MobileBuildMCP build, test or run that fails while the Xcode building isn't the pinned one, with an error another SDK or toolchain gives in its own words (a module another Swift compiled, a deployment target outside its range, an SDK it can't find, an unknown platform; for a test run whose build failed, in the build log), gets a note naming both, saying a different SDK may be the cause and giving the check's fix, once a session for each pin. It never says the mismatch is the cause. A pass gets none, and nor does a type error in a line just written or a failed assertion: a day of real use (October 30, 2026, a large modular app pinning Xcode 26.5 while 27.2 built) showed the note on every one of those, where it was noise. The Xcode MCP's failures get none, since that server builds with whichever Xcode is open.
- **CI:** only GitHub Actions workflows are read, with the local actions they use. A field report of October 31, 2026 (xcrew 0.11.0, a large modular app) had its main workflow call a composite action under `.github/workflows/actions/`, which called a second one that ran a bare `sudo xcodes select`, reading `.xcode-version`, and xcrew said CI named no version. So a `uses: ./path` line is followed, from the root as GitHub resolves it, into that folder's `action.yml` or `action.yaml`, each read once whatever uses it, and an `xcodes select` given an input (`'${{ inputs.xcode-version }}'`) isn't read as the pin file. A version is named in `maxim-lobanov/setup-xcode`'s `xcode-version` (a SemVer string, `latest`, `latest-stable` or `<semver>-beta`, from its README), `xcode-select -s` to an app, and `DEVELOPER_DIR` inside one. `latest`, `latest-stable` and ranges name no version that can be compared. A partial version covers what it begins (setup-xcode resolves `26` to the newest 26.x), a matrix passes when one of its versions covers the project's, and a line's YAML comment is skipped. A workflow can also choose its Xcode from the project's pin, as a large modular app's did in a day of real use (October 30, 2026), where xcrew said CI named no version. Now a line that reads a pin file to choose names CI's Xcode at that line, with the version in the file it reads, from the project's root: an action's `xcode-version-file`; `xcodes select` or `install` given no version, which read `.xcode-version` in the current folder (xcodes' `select` help: "Run without arguments to select the version specified in your .xcode-version file"; its install resolves through `XcodeVersionFileService`, read on main, October 30, 2026); or `cat` or `<` of it on a line that selects an Xcode, assigns what it read, or adds it to `$GITHUB_ENV`. Printing or checking the pin, hashing it for a cache key, or filtering paths by it, chooses nothing. The file must be a small regular file inside the project holding one version. A step's `working-directory` isn't followed: a pin read from a subfolder is found only when the line names its path. Xcode Cloud, Bitrise, CircleCI, GitLab and other CI systems are out of scope.

## Builds that fail because of the Mac

A build can fail on the Mac's state rather than its code, and its errors then read like the code's. Apple's docs give the fixes for such failures (committing `Package.resolved`, credentials for private packages, `-scmProvider system`, in *Building Swift packages or apps that use them in continuous integration workflows* and *Resolving common configuration and build issues*, read October 30, 2026) but never their wording. So the wording comes from real failures, captured on October 30, 2026 through MobileBuildMCP 2.7.1's MCP results with Xcode 27.2 beta 3, and committed to the test bed as `captures/environment`. MobileBuildMCP explains none of these itself; its source has no such text.

- **A corrupt module cache.** One of Clang's cached modules (in `ModuleCache.noindex`) cut short gives "malformed or corrupted precompiled file", located at an SDK header inside Xcode. One of the SDK's precompiled modules (in `SDKExplicitPrecompiledModules`) cut short gives "file '<path>.pcm' is not a valid module file". Both come with "could not build module" or "missing required module" lines, which a module that isn't there gives too, so those say nothing alone: an `import` of a module that doesn't exist gives "Unable to resolve module dependency" and nothing else. Removing both folders from the build's DerivedData, which the build log names as `-derivedDataPath`, fixed the build. A corrupt cache doesn't fail the same way twice: the same corruption gave 58 errors one time and 52 the next, so a capture is read for its kind of error, never its count. The PCH error a moved DerivedData gave in older Xcodes ("PCH was compiled with module cache path") didn't happen on Xcode 27: a moved DerivedData built, with "Stale file" warnings.
- **A simulator that's gone.** A profile naming an iPhone no simulator has reaches xcodebuild, which gives "Unable to find a device matching the provided destination specifier", with the specifier, its `name:` among them, on the next line. A name that names no platform never reaches it: MobileBuildMCP turns it away first ("Unable to determine the simulator platform for simulator name …"), and does the same for a simulator id that's gone, each with its own fix, so xcrew adds nothing to those. The simulator list (`simctl list devices available`) confirms the name is missing before xcrew says so; when it's there, something else kept the build from it, and xcrew says nothing, as it does when the list can't be read.
- **A locked build database.** In a day of real use (October 30, 2026, Xcode 26.5 on a large modular app), a build stopped mid-call left its `xcodebuild` running: stopping a MobileBuildMCP call doesn't stop the process it started. The next build of the same DerivedData failed with Xcode's `unable to attach DB: error: accessing build database "<DerivedData>/Build/Intermediates.noindex/XCBuildData/build.db": database is locked`, and `why` called it the code's. Now Xcode's wording (`accessing build database "…build.db": database is locked`) names the process holding the database, and a test's own SQLite `database is locked` stays the code's. The holder is an `xcodebuild` that `lsof -t` says has the `build.db` open or that builds into that DerivedData (compared as the file system spells it), with its pid, destination and age, and `kill <pid>`; any other holder, such as Xcode's build service, is a build still going and gets no kill. With nothing holding it, it says so; when `ps` or `lsof` fails, it says it couldn't tell. Whether a build keeps `build.db` open between writes, so that `lsof` sees it, is unconfirmed: the lock didn't reproduce to look. The test bed's field capture didn't reproduce it on Xcode 27.2, whose builds run in the shared build service, so a hand-made fixture holds the report's text.
- **A stopped call's xcodebuild goes on.** MobileBuildMCP 2.7.1's executor (`build/utils/command.js`, read October 30, 2026) spawns `xcrun xcodebuild` as an ordinary child of its server, not detached, with no abort signal, and nothing stops it when a call is stopped: the xcodebuild builds on under the server, and once the session ends and the server with it, under launchd. Under a live server a stopped call's xcodebuild and a backgrounded call's still building can't be told apart from `ps`. So the doctor's `mobilebuildmcp/no-xcodebuild-left` named, with `kill <pid>`, an xcodebuild building the project (from its working folder or its `-workspace`, not a worktree or checkout inside it) that no Claude Code is above: one under launchd past `xcrun`, which a `nohup` or a LaunchAgent build also is, so the note doesn't say who started it, or one under a server its Claude Code left. One under a live session's server it says both ways, off the prompt; one a terminal or Claude's shell started is left alone, and one that only asks a question, such as `-showBuildSettings`, holds nothing. Whether `xcrun` execs xcodebuild or stays as its parent wasn't looked at: the check reads past it either way. It's said now where it explains a failure: a build that finds its database locked names the xcodebuild holding it, with `kill <pid>` (`LockedBuildDatabase`).
- **What's the code's.** A matched error that points at one of the project's own files is the code's, however alike its words, since an `#error` can quote them. A failing test's line starts with the test's name, so it never matches either.

## A real test run's result, as MobileBuildMCP's MCP gives it

Captured on October 30, 2026 with Xcode 27.2, MobileBuildMCP 2.7.1 and the released iOS 27.2 (24B8117), through `test_sim` over MCP on the test bed's `field/` fixture, and committed as `captures/field`:

- **A blank line comes first.** The result's text opens with a blank line, then `🧪 Test`. xcrew read a test run by its first line, so no real `test_sim` result was ever read as one: no location, crash, skip or image notes, and no shortening. - **A repeated run.** With `-test-iterations 5 -test-repetition-relaunch-enabled YES`, the text lists a test's failure once for each run that failed it with a different message (`run 1 is odd`, `run 3 is odd`), or once when every run failed the same way. - **A crash with no crash log, in a run of that test alone.** A field report filed November 2, 2026 (a large modular app) had a test that crashed, run with `-only-testing` on that one test, still come back with no crash log, and the note suggested running it alone. A run whose result bundle counts one test, and whose text discovered no more, ran it alone, so its note offers what that didn't try: `-parallel-testing-enabled NO` in `extraArgs`. The bundle's `totalTestCount` counts expected failures, which MobileBuildMCP's summary line leaves out (the test bed's `serial.summary.json`: 5 tests, 1 of them an expected failure, where the text's summary counts 4; *Known issues and expected failures*), and a crash can keep later tests from running, which `Discovered N test(s)` still lists. The summary is asked for only when the one crashed test has no crash log. Apple's Xcode 10 release notes (read through Sosumi, November 2, 2026) say that "when testing in parallel on Simulator, each runner process executes on a separate clone of the selected simulator", and `man xcodebuild` (Xcode 27.2) that the option "overrides the per-target setting in the scheme". Nothing Apple documents says a run without parallel testing attaches a crash log, so neither note promises one: the older note's "may attach one" has no recorded basis and is kept as it was for other runs.
- **A crash under System Failures.** The result bundle can file a test's crash under a suite of its own, `System Failures`, as a test case named `xctest (<pid>) encountered an error` whose only message names the test last: `Crash: xctest at implicit closure #1 in Suite.test()`. The test itself is no node. A field report of October 31, 2026 (xcrew 0.11.0, iOS 26.5 simulator, a large modular app) had a crash inside an assertion's autoclosure filed that way. The same test on the iOS 27.2 runtime (the test bed's `captures/raw/system-failure-crash`, November 2, 2026) was filed under its test. MobileBuildMCP takes a Test Suite's name as the suite and leaves a test case's name with no `/` or `.` whole (MobileBuildMCP 2.7.1, `utils/xcresult-test-failures.js:44-68`, `utils/xcodebuild-line-parsers.js:29-48`), and writes `suite / test: message` (`utils/renderers/domain-result-text.js:136-139`). So its text says `System Failures / xctest (<pid>) encountered an error: Crash: …`, and xcrew reads that line as the failure of the test its message names. The crash note's frames come from the crash log attached to the test, asked for by the test's id; this shape's id is the `xctest (<pid>)` case's, and no capture has a bundle in that shape yet.
- **Targets.** The test list files each test case under its unit or UI test bundle, named as its target. The report carries a failing test's target, and the ledger matches a later selection against it.
- **A skip's message has two prefixes.** The result bundle's test list writes `Test skipped - waits for the farewell screen` for XCTest's `XCTSkip` and `Test skipped: skipped on purpose` for Swift Testing's `.disabled("…")` (the test bed's `captures/raw/serial.tests.json` and `shapes.tests.json`, v0.8.13). xcrew shows the reason without either.
- **Durations are written in the Mac's locale.** xcresulttool's answers kept beside the test bed's raw captures (`captures/raw/*.tests.json`, `.summary.json`, `.details.*.json`; test bed v0.8.13, read October 31, 2026 on a Mac whose locale writes a decimal comma) write durations as text in that locale: `"duration":"Ran for 0,0056 seconds"`, `"duration":"0,0056s"`. xcrew reads no such text. It reads a skip's time from `durationInSeconds`, a run's start from `startTime`, and the counts `totalTestCount`, `passedTests`, `failedTests`, `skippedTests` and `expectedFailures`, all JSON numbers, so a comma-decimal locale changes nothing it reports. The replay goldens, recorded from those answers, show a skip's time as `(0.014s)`.

## Known issues and expected failures

`xcresulttool get test-results tests` files a Swift Testing test that recorded a known issue (`withKnownIssue`) as an `Expected Failure`, as it does an XCTest test under `XCTExpectFailure`, and the summary counts both in `expectedFailures`. Only the test case's `nodeIdentifierURL` tells them apart: `test://com.apple.xcode/SwiftTesting/KitTests/ShapesTests/knownIssue()` for Swift Testing, `test://com.apple.xcode/Feature/FeatureTests/ProbeTests/testExpectedFailure` for XCTest, the target's path. Seen with Xcode 27.2 and iOS 27.2 on the test bed's `captures/raw` bundle answers (`shapes.tests.json`, `serial.tests.json`, October 31, 2026); Apple's docs describe neither the URL nor the result. So the note names each test by the API it used, and names both when the list can't be read. `KnownIssueNoteTests` pins it on those answers.

**MobileBuildMCP's count leaves them out; the bundle's total and xcodebuild's count have them.** Apple's docs for `XCTExpectFailure` and `withKnownIssue` don't say how such a test is counted, and xcresulttool's summary schema (0.5.0) names `totalTestCount` and `expectedFailures` without saying what either holds, so this rests on the source and the captures. MobileBuildMCP reads a run's counts from the bundle's summary, `passedTests`, `failedTests` and `skippedTests` only (`utils/xcresult-test-failures.js:7-27`), and writes their sum as the total (`utils/renderers/domain-result-text.js:1460-1463`), so `expectedFailures` is in no count of its text (MobileBuildMCP 2.7.1, read November 3, 2026). On the test bed's raw captures (v0.8.25, read November 3, 2026; Xcode 27.2, the iOS 27.2 runtime, MobileBuildMCP 2.7.1; macOS 27.2, 26B123, by the two crash reports among them), the six with an expected failure have a bundle `totalTestCount` one above the text's total, that test: `serial`, `retry` and `timing` (`ProbeTests/testExpectedFailure()`), and `shapes`, `shapes-iterations` and `shapes-configurations` (`ShapesTests/knownIssue()`), the one test case each test list files as an `Expected Failure`. The other six with a summary agree, and passed, failed and skipped agree on all twelve. xcodebuild's log counts the test as the bundle does: `Executed 5 tests, with 1 test skipped and 2 failures (0 unexpected)` for `serial`'s 5, Swift Testing's `Test run with 6 tests` for `shapes`' 6. So the bundle's total is the run's count of tests, and the text's is that less its expected failures. xcrew's summary takes the text's counts when it has some, so its total leaves them out too, and the note on them names them with the bundle's total.

Without the summary's three counts, when MobileBuildMCP found no bundle, its read failed or timed out, or the summary lacked one, it counts from xcodebuild's log instead (`utils/xcodebuild-domain-results.js:253-260`), and the log's counts put the expected failure in: as passed for XCTest, as failed for Swift Testing, whose run line counts issues, the known one too (`with 2 issues (including 1 known issue)`). Replayed through MobileBuildMCP's own log parser on November 3, 2026, `serial` gives 2 passed, 2 failed, 1 skipped, and `shapes` 3 passed, 2 failed, 1 skipped, where the bundle has 1 failed. xcrew's note, which says expected failures count as neither passed nor failed, holds only for the bundle's counts. The log's own count is the run's only for a run of one configuration, no retries and no crash: `retry`'s says `Executed 8 tests`, each run of a retried test, for 5 tests; `configurations` and `shapes-configurations` print theirs once for each configuration; and in `timing`, after `Restarting after unexpected exit, crash, or test timeout`, the crashed test's class prints `Executed 0 tests` and the totals that follow, 5, leave the crashed test out of the bundle's 6.

## A failed snapshot test's images

A failing snapshot test's message says the render doesn't match, and at most where the reference and the new render are; the difference image exists only in the result bundle. Read October 30, 2026: swift-snapshot-testing 1.19.7 attaches `reference`, `failure` and `difference` images on a failure (`UIImage.swift`, `NSImage.swift`; under Swift Testing through `Attachment.record`), and iOSSnapshotTestCase 8.0.0 attaches `Reference Image`, `Failed Image` and `Diffed Image` (`FBSnapshotTestCase.m`). `xcresulttool export attachments` (Xcode 27.2) writes each attachment with a `manifest.json` naming its `exportedFileName`, `suggestedHumanReadableName` and `isAssociatedWithFailure`.

Captured on October 30, 2026 with Xcode 27.2 (27B52), MobileBuildMCP 2.7.1, on an iPhone 18 Pro Max simulator on iOS 27.2 (24B8117), from one failing test of each library and framework, through plain `xcodebuild test` and MobileBuildMCP's `test_sim`, committed to the test bed as `captures/snapshots`:

- **Not associated with the failure.** Every image of both libraries, under both ways of running, is `isAssociatedWithFailure: false`; only the issue description is `true`. So `--only-failures` drops them: xcrew exports a failed test's attachments without it, and lists images only for failed tests.
- **Names.** A suggested name is `<name>_<n>_<id>.png`. Under XCTest `n` counts 0, 1, 2 in the order reference, failure, difference; under Swift Testing each is 0, in no set order. So xcrew orders by the words the names begin with (`ref`, `fail`, `diff`), keeping each comparison's three together in a run repeated with `-test-iterations`, then the rest in the order attached.
- **Extensions.** swift-snapshot-testing's XCTest images export with no file extension, though each is a PNG and its suggested name ends `.png`. So xcrew tells an image by its suggested name or its first bytes, never by the exported file's extension, and keeps it under its suggested name, with the extension its content says when the name has none, so Read opens it as an image. Only the formats Claude takes as images count: PNG, JPEG, GIF and WebP.
- **`hasMediaAttachments` doesn't say whether a test attached images.** Read October 30, 2026 with Xcode 27.2 (27B52), xcresulttool 25407: `xcresulttool get test-results test-details` answers `hasMediaAttachments`, which could have spared the export for a failure with no images. It's unreliable both ways. In the snapshot capture's own `test_sim` bundle it was false for swift-snapshot-testing's XCTest test, whose three images were there, and true for its Swift Testing test and iOSSnapshotTestCase's. In the test bed's UI-test captures (v0.7.0), it was false for all four failed tests under both `xcodebuild test` and `test_sim`, though each attached screen recordings and UI snapshots. So every failed test's attachments are exported, up to the lookup cap, and a test pins the UI-test answers.
- **What's kept, and its cost.** A run's kept images go under xcrew's cache, one folder a run, and a run's are pruned after two weeks or once all of them take more than `FailureImages.keptBytes`. Each run's folder records the bytes its kept files take, in `.size`, so pruning reads one small file a run rather than every file of two weeks of runs. Each writer records its run once its writes are done: the notes after all of a run's tests' images are kept, `look` after all the tests it looks at, which it looks at side by side, the evidence block after all its entries. Two measures of one run at once could record too few, since one taken before another's write would land last. Recording puts the run folder's date back, since that date is its age; a run kept before the record is measured at its first prune.
- **Swift Testing and UIKit.** A Swift Testing test runs on the cooperative pool: one that made a `UIView` without `@MainActor` crashed in UIKit's main-thread check.

## A failed UI test's screen

A UI test's failure message names the query that failed, not what was on the screen. Read October 30, 2026: `xcresulttool get test-results activities` (Xcode 27.2, schema 0.5.0) lists each run of a test with its `device` and `testPlanConfiguration`, and each step with its `startTime`, `isAssociatedWithFailure` and attachments; `export attachments` names each attachment's `configurationName`, `deviceId` and `timestamp`. WWDC25 session 344 says a test plan keeps videos and screenshots only for failing runs by default.

Captured on October 30, 2026 with Xcode 27.2 (27B52), MobileBuildMCP 2.7.1, on an iPhone 18 Pro Max simulator on iOS 27.2 (24B8117), from five XCTest UI tests under a test plan of two configurations left at Xcode's defaults, through plain `xcodebuild test` and MobileBuildMCP's `test_sim`, committed to the test bed as `captures/uitests`:

- **A recording, no screenshot.** Each failed run keeps a screen recording and no screenshot image; a passing run keeps nothing. The recording starts with the test and stops at the failure, within 0.1 s of the failing step's `startTime`. So xcrew shows the recording's last frame as the screen at the failure.
- **The failing step.** In `activities`, the step that failed is the one with `isAssociatedWithFailure: true`, at the top level of its run.
- **Per configuration.** A test failing under one configuration only has a failed run for that one and a passed run for the other, and each attachment names its configuration and device, so xcrew pairs each failed run with its own recording.
- **Which run.** MobileBuildMCP 2.7.1 keeps a test run's bundle in its workspace's `result-bundles`, named with its server's pid as `_pid<server>_`, and writes `<bundle>.mobilebuildmcp-completed` beside it once the run has finished (`utils/result-bundle-path.js`, `utils/test-common.js`, read October 30, 2026); it removes bundles three days old. So `xcrew look` reads the newest finished bundle of this session's own servers, and the newest bundle at all only where none has the mark.
- **The hierarchy.** When a query fails, XCTest attaches the app's accessibility hierarchy as text, one element per line indented two spaces a level: its type, its address, its frame, then `identifier: '…'`, `label: '…'` and `value: '…'` when set. Beside it sit an archived UI snapshot and the query's debug descriptions, which are text too. So xcrew tells the hierarchy by that shape, and falls back to the attachment whose suggested name begins `App UI hierarchy` to show XCTest's own text.
- **Only the app's elements.** Every element of that hierarchy carries the app's `pid` (the capture's `<AX element pid: 26159…>`): it's the app's process alone. A field report of November 2, 2026 (a large modular app) had a system alert asking to send notifications cover the app in a failed UI test's screenshot, while the list showed only the app and its buttons. So when the query found nothing and the failure has a screen, `look` says the elements are the app's only and a system alert shows only in the screenshot.
- **A run's own attachments.** In `get test-results activities`, each step lists its attachments with a `uuid`, and `export attachments` names each attachment's file by that id: on the capture's `test_sim` bundle, all 14 attachments in `testRenamedLabel`'s activities had a file of that name, its extension apart. So xcrew takes a run's recording and hierarchy from that run's own steps, not by time or by the export's manifest, and a repeated run never shows another run's. The capture holds no label with an apostrophe in it, so whether XCTest escapes one is unknown: xcrew reads a quoted value either way, ending it at the quote that's followed by the next attribute.
- **Export by name.** `xcresulttool export attachments --filter` (25407) matches the attachment's suggested name, not its exported file name: on a snapshot run's bundle, `reference*` exported the two reference images, `*.png` all nine images, those exported with no extension too, and `0*`, the shape of an exported name, none. A filter can't select by content, and the hierarchy's suggested name has no extension, so `look` exports a test's attachments unfiltered.
- **The cost of an unfiltered export.** On the capture's own `test_sim` bundle (9.5 MB, APFS, macOS 27.2), exporting one failed test's attachments took 0.046 to 0.053 s and 1.3 to 2.7 MB over three runs of each of the four failed tests, the same time as exporting only its recordings, which were 98 to 99 % of the bytes. `xcrew look` over the whole bundle took 0.53 s.
- **The last frame.** A recording writes a frame only when the screen changes, so its last frame can sit seconds before its end (one 7.29 s recording's last was at 4.667 s), and still shows the screen at the end. Asked for a frame near the end with any tolerance before it, `AVAssetImageGenerator` returned the keyframe before (7.0 s instead of 7.667 s in another). So xcrew asks for the frame just before the end with no tolerance, and measures how far before the failure it is from the recording's end. A test reads a captured recording's last frame, so a change in how frames are found turns it red.

## What the doctor keeps

The doctor keeps what xcrew needs to run. Most checks whose answer matters only when something fails moved to where it fails: storage and worktree leftovers to `xcrew space`, and which Xcode builds to the failure it explains. Checks that no longer held were removed. A plan to cut xcrew further (#332) would also have removed `xcrew graph`, `xcrew concurrency`, `/xcrew evidence`, the CI Xcode check and the changed-line notes. It wasn't adopted (#354), and they stay.

## Which session the doctor checks

Two checks are about the session the doctor runs in: whether its rules are the running xcrew's (`xcrew/briefing-current`), and whether xcrew's mod is loaded in it (`xcrew/mod-loaded`). Claude Code's docs (code.claude.com/docs/en/env-vars, read November 2, 2026) say of `CLAUDE_CODE_SESSION_ID`: "Set automatically to the current session ID in Bash and PowerShell tool subprocesses, hook command subprocesses, and stdio MCP server subprocesses. For Bash, PowerShell, and hooks this matches the `session_id` field in the hook JSON input and is updated on `/clear`." So the doctor Claude runs through Bash, and the start hook, name the same session; from a terminal of one's own the variable is absent and both checks skip. The docs don't list the processes a mod starts, so the mod names its session itself, `--session` on its doctor read.

- **The stamp:** a small folder a session in xcrew's cache, `sessions/<id>/`, with one file for each writer. `xcrew hook session-start` writes `briefing`, the version whose rules it gave; the mod's doctor read writes `mod`, its version, before its checks run, so no check of that run finds it missing. The two run at once as a session starts, so each writes only its own file: one file for both, read, changed and written back by each, could lose whichever was written first. A stamp an older xcrew kept in one file, `sessions/<id>.json`, is still read for the field its writer hasn't written again. The SessionEnd command hook removes it, as the session's facts end with it. A stamp a crash leaves is removed after two weeks, the age xcrew keeps its other unused cache entries; a choice, not a measurement, which #395 reviews.
- **A stale briefing:** `/reload-plugins` reloads the mod, whose session start runs again, but no start hook runs, so the rules Claude was given stay the old version's. A briefing version other than the running one warns, with a restart as the fix.
- **A conversation that changes under the process:** after a `/clear` or a resume, Claude Code goes on in the same process under another session id. The engine's types (Claude Code 2.1.314, `session.end`, read November 2, 2026) say of `clear` that "no `session.start` fires for it", and of the ending session's id that "after a `/clear` or a resume the process goes on under another". So the mod starts over on `session.end` with either reason, `clear` or `resume`: it forgets the pin it named and the warnings it showed, and reads the doctor on the next prompt, since a CLI call can't finish within that event's bound.
- **A mod that hasn't reported:** a warning, not a failure: the mod reports on its first doctor read, which a doctor run can come before, as while the CLI builds after an update. The mod's first read that fails is tried once more on the next prompt. Without the mod the line above the prompt is gone too, so only the doctor's text can say so.

## Worktree sessions

A `claude --worktree <name>` session works in `.claude/worktrees/<name>`, on branch `worktree-<name>` ([worktrees](https://code.claude.com/docs/en/worktrees.md)). The docs say neither where a plugin's MCP servers start there nor what `${CLAUDE_PROJECT_DIR}` expands to in their arguments.

Measured on October 30, 2026 with Claude Code 2.1.314 on macOS 27.2, in interactive sessions driven through a pseudo-terminal. The setup was a throwaway git repository and a copy of this plugin reduced to its MobileBuildMCP server, whose launcher logged its process, working directory, argument and environment. Nothing booted a simulator.

- **A plain session** starts the server once. Its working directory, its argument and its environment's `CLAUDE_PROJECT_DIR` are all the project's root.
- **A worktree session** starts it twice, in the same second, and both stay up for the session. Both run in the worktree with `CLAUDE_PROJECT_DIR` set to the worktree. One gets the worktree as its argument. The other gets the original root, so `libexec/mobilebuildmcp-server`, which `cd`s into its argument, runs that one on the main checkout and its config.
- **Claude's tool calls reach the worktree's server.** With the root's working copy naming one profile and the worktree's config another, MobileBuildMCP's `session_show_defaults` reported the worktree's, on three runs. Builds in a worktree session therefore use the worktree's config and sources. The other server stays idle in the main checkout for the session.
- **Hooks see the worktree.** A `SessionStart` command hook ran in the worktree with `CLAUDE_PROJECT_DIR` set to the worktree. So xcrew takes the worktree as the project. The doctor's `mobilebuildmcp/config-loaded` picks the server whose working directory is the worktree, which is the one serving. The idle server writes nothing in the worktree's MobileBuildMCP workspace, so `RunLog` isn't misled either.
- **A worktree has no MobileBuildMCP config of its own.** Setup keeps `.mobilebuildmcp/` out of git through `info/exclude`, which a repository's worktrees share. `mobilebuildmcp/project-config` fails there and names setup.
- **Nor a generated project.** A generator's output is kept out of git, so a fresh worktree of a Tuist or XcodeGen project has manifests and no workspace beside them. A field run of November 2, 2026 (xcrew 0.12.0, a large Tuist app) found it only by comparing the config's path with the folder after setup. So before setup, `mobilebuildmcp/project-config` names the generate with setup when no container sits beside the nearest manifests, by the rule setup uses to pick its container: a module's own project below doesn't count.

`claude -p` sometimes ends before a plugin's servers start, so the duplicate shows only intermittently there. These measurements come from interactive sessions.

`xcrew setup --worktree` also gives the worktree simulators of its own, unless `--no-simulator`. Each simulator the main checkout's profiles use, found by the id a profile names, else by its name on the newest runtime, gets one. While it's shut down it's cloned (`xcrun simctl clone`), with its apps and data; while it's booted, which `simctl clone` can't take, or with `--fresh-simulator`, one is made fresh on its device type and runtime (`xcrun simctl create`). None is booted. It's named `xcrew · <main repository's folder> · <worktree's folder>`, with the device type after it when the profiles use more than one; the repository folders, not the project's, so an app in `ios/` still names each worktree apart. The fixed prefix is what lets `xcrew space` tell these from a person's own. One already made is used again. Each profile then names its own by id, once: plain setup writes both `simulatorName` and `simulatorId`, and one mapping holding a key twice isn't valid YAML. Two clones with the same folder and worktree names would share a name, and so a simulator. On October 30, 2026 (Xcode 27.2), a throwaway repository's worktree got `xcrew · Shop · feature-x` (iPhone 18 Pro, iOS 27.2), shut down, and a second setup reused it; it was then deleted.

**Clone or create** (one run each, so suggestive, not proven). On October 30, 2026 (macOS 27.2, Xcode 27.2, the released iOS 27.2 runtime, the test bed's capture simulator), a fresh simulator, booted once with Settings launched once, crashed `AppIntentsLiveEntityService` and `SettingsSearchReindexService` within a minute, as fresh devices on that runtime do in the test bed's captures. Shut down, cloned, and the clone booted once with Settings launched once: no crash report in the next minute. `xcrun simctl clone <device> <new name>` printed the clone's id on stdout, which setup reads. `simctl help clone` says nothing of a booted device, and cloning one wasn't tried: setup clones only a shut-down simulator and makes a booted one's fresh. Shutting a simulator down leaves `SIGKILL` reports with `XPC_EXIT_REASON_SIGTERM_TIMEOUT` from its daemons; those are the shutdown's, not crashes.

**Memory per simulator**, the same day and setup, on a 32 GB Mac. Settled and idle, the simulator's process tree under its one `launchd_sim` was 259 processes. `footprint` summed it to 11,247 MB, while `vm_stat` (active, wired and compressed pages) showed 6,644 MB more in use than before boot. With the field app running: 262 processes, `footprint` 11,699 MB, `vm_stat` +6,193 MB. The two disagree by about 40%, and neither is taken as the figure: `footprint` counts each process's dirty and compressed memory, while `vm_stat`'s change is the whole Mac's, net of what else was freed or compressed meanwhile (unverified). A first attempt that summed `ps`'s resident memory came to about 28 GB, counting the simulator's shared libraries once per process, and isn't a measure. The doctor's check that weighed the booted simulators against the Mac's memory rested on these figures, and is gone for that reason.

**Which simulators are a worktree's.** A simulator's name holds only the main checkout's folder name and the worktree's, so it can't tell two clones of one folder name apart, and setup takes the worktree's name from the folder Claude Code gives it, which can differ in letter case from the path `git worktree list` keeps. On October 30, 2026 (macOS 27.2, APFS case-insensitive), in a scratch repository, `git worktree add ../trees/MyTree` then `cd trees/mytree` gave `mytree` from both `pwd` and `/bin/pwd`, while `git worktree list --porcelain` still printed `MyTree`. So setup records each simulator it makes or reuses, by udid and the worktree's canonical path, in `<git common dir>/xcrew/worktree-simulators`, which every checkout of the repository shares. `xcrew space` names a simulator to delete only from that record, comparing canonical paths (`ProjectLayout.canonical`, which resolves letter case), and setup finds one made earlier by the record before its name. A simulator made before the record existed is never named.

## No budgets

No work of xcrew's stops, is killed, is skipped or hands over less because a time ran out or a list grew long: a call runs to its end, and a read that fails says so (*Failed reads*), and a session hook builds nothing (*The session hooks*). xcrew measures, and doesn't block on what it measures. What limits are left are the platform's, which xcrew can't move; each is below with its source, and xcrew adds nothing of its own on top.

- **The CLI.** No command it starts has a time limit, and nothing hands the CLI a deadline: `DeadlineRunner` and `XCREW_WITHIN_MS` are gone, and `CommandRunning.run` takes no timeout. A command whose task is cancelled is stopped with the children it started, as its answer is no longer wanted; nothing else stops one, and the CLI cancels its work when it gets SIGTERM or SIGINT (*Stopping a program*). The evidence reads every run of the branch, and the report reads its failures and its coverage whole. A wait the CLI can't see the end of is said while it lasts: the doctor waits on a new Xcode MCP bridge, which Xcode may hold on its approval dialog, and writes `xcrew progress: ` and what it waits on to standard error, which `/xcrew doctor` shows in the status line until the doctor answers.
- **The mod.** Every call on the CLI is spawned (`$.process.spawn`) and read to its end, so `$.process.run`'s limits don't apply: "timeout 30 s by default, ten minutes at most", and "each stream's first 4194304 bytes" (`$.process.run`, the mod API's types, Claude Code 2.1.314). A call on a result waits for the CLI however long it takes, and a call made while the CLI is still being built waits for that build through the shim, whose lock keeps to one build at a time (*Building after a reload*).
- **A hook waits only on `$` calls.** The mods API gives a hook a budget of its own time per dispatch: "A hook's budget per dispatch, from its call to its return; past it the hook is absent (its `.catch` asked, else `next(e)` run on its behalf)", `ms: 10_000`, with a `.catch` handler's grace `catchMs: 1_000` (`HookBudget`, the mod API's types, Claude Code 2.1.314). What counts: "a `next` or `$` call in flight does not count; a `$.clock.sleep` does" (the plugin reference, *Work that outlives a dispatch*). So no hook awaits a promise the module keeps, however it's reached, which a ManifestTest pins. 0.14.0's `/xcrew doctor` answered "couldn't answer: it failed" after an update: its wait for the build raced a shared promise inside the hook, past the 10 s, and the engine dropped the hook, whose `.catch` words a drop with no message as "it failed" (`HookFailure`: "absent for a timeout with nothing rejected"). That cause is supported by the docs, not reproduced: the test engine doesn't meter the budget. 0.13.1 kept one such wait too, the shared shim question, which the same rule removes.
- **Two write chains stay.** The ledger's writes and the run durations' each wait for the one before, so two runs ending together don't lose each other's entries: the store has no atomic read-modify-write. That is read from the mod API's types, which give `$.store` `get`, `set`, `delete` and `keys` and no operation that reads and writes at once; no doc says so outright. A chain's links are store calls alone, a few milliseconds each; what the CLI says for a ledger write, the branch and a repeated run's flaky marks, is read in the run's own hook first, from the ledger as the writes queued before left it, and again when another run queued a write meanwhile, so two repeated runs ending together each count. A ManifestTest pins both chains.
- **The size and count caps that skipped work are gone.** Every failed test is looked up and every skipped test the text leaves out is added (`FailureNotes.mostLookups`, 10); `look` reads every failed test for a recording (`Look.mostScanned`, 40); the briefing reads every shared scheme's test plan (`TestPlans.mostSchemes`, 50); a run's log is read whole for its verdict (`RunLog.endBytes`, its last 1 MB); a log's scheme, its DerivedData and a workspace's root are read up to the line that names them, line by line, wherever that is (64 lines, 64 KB, three logs and four folders up); a manifest is read up to the line that imports ProjectDescription (8 KB); a pin file is read whole (1 KB). A line read line by line is read once, however long it is.
- **Three bounds stay, as they aren't caps.** `UIQuery.stepsSearched`: a query further back than the last two steps passed, so it isn't the failing one, and searching further would name the wrong element (`UIQueryTests.theQueryIsTheOneTheFailureOrItsLastStepsName`, its fourth case). `Report.noticeLimit`: Claude Code's notice for a saved result is short, so a long result that merely names a saved file isn't a notice (`ReportsTests.aLongResultThatNamesASavedFileIsNotANotice`). `ProjectLayout.searchDepth`: MobileBuildMCP's own project discovery stops at depth 3 (2.7.1, `mcp/tools/project-discovery/discover_projs.js`, `DEFAULT_MAX_DEPTH = 3`), so a container it finds is one xcrew finds; the launcher's quick look for a pin reaches as far, as the CLI's own rule does (a ManifestTest pairs them).
- **What every shortened list says.** A list that names a few and counts the rest says where they all are, or, where nothing keeps them, "no list of them is kept", so nothing reads as whole when it isn't. The card keeps every line.
- **What else stays.** `SystemCommandRunner.grace`, 1 s, how long a finished program's pipes are read for a child that outlives it holding them, and `StandardInput.idleLimit`, 2 s, how long standard input may sit open with nothing arriving: each bounds a wait on an open pipe, and neither cuts work. `HEAD_FRESH_MS` (5 s) and `RECHECK_MS` (30 s) are how long an answer is trusted, and stop nothing. A binary plist is read whole, each object once however many references share it; only one that refers to itself, past any keyed archive's nesting, reads as nothing.
- **The platform's limits, kept and recorded.**
  - Claude Code's hooks: "Defaults: 600 for `command`, `http`, and `mcp_tool`" seconds, and "Claude Code cancels a `command`, `http`, or `mcp_tool` hook that reaches its `timeout`", except an async one (hooks reference); SessionEnd's 1.5 s is in *The session hooks*. xcrew's `hooks.json` sets no timeout of its own.
  - Its Bash tool: `BASH_DEFAULT_TIMEOUT_MS` "(default: 120000, or 2 minutes)", up to `BASH_MAX_TIMEOUT_MS` "(default: 600000, or 10 minutes)" (environment variables reference). A CLI run through Bash past it moves to the background.
  - An MCP server's start: `MCP_TIMEOUT`, "Timeout in milliseconds for MCP server startup (default: 30000, or 30 seconds)" (the same reference). The MobileBuildMCP launcher's wait for the pin is inside it; the read took 10 ms at the median, 277 ms at most (November 3, 2026, M1 Max, macOS 27.2, the release build, 30 runs).
  - A result past 50,000 characters is saved to a file (*Test reports from the two servers*).
  - `claude plugin test`'s own limit on a test, 5 s, which a test that waits longer meets ("timed out after 5000 ms", seen November 2, 2026, Claude Code 2.1.314); the mod's tests run on a fake clock and meet it only when one hangs.
  - GitHub Actions' limit on a job: `timeout-minutes`, "The maximum number of minutes to let a job run before GitHub automatically cancels it. Default: 360" (GitHub's workflow syntax reference, read November 3, 2026); xcrew's workflows name none of their own.
  - mcs's configure step: mcs 2026.10.31 runs the techpack's `mcs/configure.sh`, which execs `bin/xcrew setup`, on every project sync with `timeout: 60` (`Sources/mcs/ExternalPack/ExternalPackAdapter.swift`), and a script past it fails the sync with "Script timed out after 60 seconds". That limit is "enforced best-effort: `terminate()` sends SIGTERM to the direct child only" (`Sources/mcs/ExternalPack/ScriptRunner.swift`); by that, a build the shim started under its lock would run on to its end, which wasn't measured. The first sync after an update builds the CLI before setup runs, 13.5 to 15.4 s (*Building after a reload*).
- **Measured, as evidence.** None of these numbers gates anything.
  - **Calls on a result.** Measured on November 2, 2026 (M1 Max, macOS 27.2, APFS, Xcode 27.2, the release build, 30 runs each, median and p95), as processes on the test bed's captures, each report reading its run's real result bundle: the report on a test run took 56 to 777 ms at the median and 58 to 788 ms at p95, the slowest a crashed run's, whose failures and images are read; on a build, 57 and 61 ms; `note` 14 and 15 ms; `session` 14 and 16 ms; `project --profiles`, `--hash`, `--manifest` and `--generated` 10 to 17 ms and 12 to 21 ms; `affected` on the test bed's field project 53 and 58 ms. Measured the same way on November 3, 2026, the reads before a call: `project` 11 and 14 ms, `project --xcode` 62 and 65 ms, `project --branch` 18 and 19 ms, and `flaky` on one mark 9 and 13 ms. A large app's runs weren't measured.
  - **The report with coverage.** Measured on November 3, 2026, the same Mac and way, on the test bed's largest result bundle holding coverage (9.5 MB, `captures/uitests`: a UI test run of 4 failures and 1 pass, its screenshots exported for the failures), from the checkout its coverage names: the report took 778 ms at the median and 794 ms at p95, reading the failures, the content availability (27 and 28 ms) and `xccov`'s coverage report (666 and 679 ms). That checkout's branch changes nothing, so no file's lines were read. Each file's read (`xccov view --archive --file`) took 663 to 668 ms at the median and 669 to 693 ms at p95, nearly all of it `xccov`'s start. A branch that changed all three files the coverage holds adds at most their sum, 2.0 s, if the three ran one after another; the pool runs them side by side, one a performance core (8 on this Mac).
  - **A large log, read whole where its last 1 MB was.** A 30 MB log made from the test bed's real build log repeated, timed 30 times a command (November 3, 2026, M1 Max, macOS 27.2, release builds from before this change, which read the last 1 MB, and after it): `xcrew report --log` took 24 ms at the median and 30 ms at p95 before, 486 and 490 ms after, the whole log read for its verdict; `xcrew why --log` took 19.7 and 19.9 s before, 19.8 and 22.0 s after, as it always read the whole log, about 0.67 s a MB, a cost of its own this change doesn't touch.

## The session hooks

Read November 3, 2026, in Claude Code's hooks reference and its environment variables reference.

- **SessionEnd has 1.5 s, which a plugin can't raise.** "SessionEnd hooks have a default timeout of 1.5 seconds. It applies when you exit, run `/clear`, or switch sessions with interactive `/resume`", raised by a per-hook `timeout` up to 60 s, but "Timeouts set on plugin-provided hooks don't raise the budget"; only the person's `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS` does. xcrew's `"timeout": 10` never applied: its session end always had 1.5 s, and after an update the shim spent it building the CLI, so Claude Code cancelled it ("Hook cancelled"). Now the shim's shell does a session's end before it hashes anything: it moves the session's stamp folder aside in one rename and removes it, with the briefing it left due, and starts no CLI. A cancel leaves the stamp there or gone, never half of it; one left aside is pruned with the other stamps.
- **SessionStart holds Claude's first answer.** "Claude's first response still waits for the hooks to finish, so their context reaches Claude." So the start builds nothing: with a build there it briefs at once; with none it says in one line that the CLI is being built and the briefing follows with the next turn.
- **The late start brings the briefing.** "After the background process exits, Claude Code delivers the `additionalContext` and `systemMessage` fields from the hook's JSON response to Claude on the next conversation turn", for a hook with `"async": true`, which "Claude Code doesn't enforce `timeout` on". The late start is that hook: it builds or waits for the build through the shim, then gives a briefing a start left due, or says the build failed. The two hooks of a start run side by side and share no id of the start, so each start that leaves its briefing due names the file for itself (`<session>.due.<pid>`) and writes in it the Claude Code it runs under, its process id and start time; a late start takes one briefing its own Claude Code's starts left, by a rename only one taker can make. Two starts while the CLI builds, as a compaction during the first build, so leave two, and each late start gives one. A briefing a Claude Code that's gone left, as one that crashed while the CLI built, is no late start's to take, and a start that finds a build briefs at once and clears what's due. The Claude Code is found as the hook's ancestor named `claude`; one run as a Node script is named `node`, and then every start reads as the same, as before this. Claude Code also skips an async SessionStart hook's output when it "matches what Claude last received from that hook", and delivers it again after a compaction or `/clear`.
- **What Claude knows before the build ends.** A first prompt sent while the CLI is still being built is answered without the briefing: Claude has the one line saying the CLI is being built and that the briefing follows, and the MCP servers' own instructions, but not the routing rules, the card or the doctor's problems, which come with the next turn.
- **No timeout of xcrew's.** `hooks.json` names none, so Claude Code's own governs: 600 s for a command hook, 1.5 s for SessionEnd.

## Failed reads

A read xcrew makes of its CLI that fails, as one that couldn't run or that gave no answer xcrew could read, says so, with why, rather than leaving xcrew to go on without it. A read a call waits on says it with that call's result, each time; a read nobody waits on, as the band's, says it once with the next result of xcrew's tools, until it answers. Either shows on the line above the prompt from its first failure for as long as a warning does. A read is one read whatever moments or run its arguments name (`readKey` leaves out the values of `--since`, `--until`, `--log` and `--expected`), so an answer at other times takes back the failure, its line still to be said and its warning. A command that prints nothing and ends well, as `card --save` does, has answered nothing and hasn't failed.

## Runs that overlap another checkout's

Runs that overlapped another checkout's build or test took longer for it. A field report of November 2, 2026, with two checkouts of one app testing at once, had one module's runs alone take 52 to 63 s, and two that overlapped the other checkout's build take 78 and 64 s. Both went into the usual time, which then read 1:09. So a run that overlapped one is kept out of the usual times, its own and a failed run's alike.

- **What overlapped.** `xcrew runs --overlapped`, told the run's start and end, names the project's other worktrees (`git worktree list`, as `xcrew runs` reads them) with an xcodebuild log in their MobileBuildMCP workspace opened before the run ended and last written at or after its start, or written less than `OtherRuns.quietFor` before its start with no verdict, as a run through a long link or a simulator's boot is. The run ends its server's own duration after the call's start, or, without one, when the call answered, or, for a call moved to the background, when its notification was read. A log is opened when MobileBuildMCP names it (*Which log is the run's*), and last written when its run last printed, so this covers a run that started before, during, or ended since. It uses the same logs as the line about other worktrees' runs: a Swift package's build, which writes no verdict, isn't one.
- **Off the result's path.** A `tool.call` hook's return is the result Claude reads, so anything the hook awaits holds Claude. Claude's result is the one thing that has to come first, so the mod returns it and asks in a task it doesn't await. The run's ending, on the line above the prompt, in its row, in a toast and, for a long run, in a notification, is shown in that task once the answer comes, compared with the usual time only when nothing overlapped; then the time is written. The whole call, the CLI's start included, took 17 and 25 ms (median and p95) at 1 worktree, 23 and 25 ms at 8 worktrees of 40 logs, and 63 and 67 ms at 20 of 200 with a run going in each (the same day and Mac, a release build, 30 runs each): under the 0.1 s at which a response stops feeling instant (Nielsen, *Usability Engineering*, 1993, ch. 5). A CLI that doesn't answer holds the ending until it does, the CLI's build first when there's none; the band shows the run going until then. A run that starts meanwhile keeps its place on the band, and the earlier run's ending goes to a toast; a failure the person closed meanwhile stays closed. Another run of the scope can end while the check is out, so each scope's writes go one after another, each reading the history again just before it writes, and neither run's time is lost.
- **What it costs.** It runs after every build and test: two git processes for the worktrees, then each other worktree's logs, listed once with their dates, and only those written lately have their names read. Measured on November 2, 2026 (M1 Max, macOS 27.2, APFS, the check in process in a debug build, real git, a throwaway home with MobileBuildMCP workspaces whose logs were last written a day before; 30 runs, median and p95): at 8 worktrees of 40 logs, 92 and 95 ms before this listing, 17 and 18 ms after; at 20 worktrees of 200 logs, 931 and 949 ms before, 48 and 51 ms after, and 57 and 61 ms with one log in each worktree still going. MobileBuildMCP keeps logs for 3 days, up to 10,000 files, so a worktree under heavy use can pass 200.
- **Its limits.** It sees the project's own worktrees only: another project's build on the Mac, Xcode's own build, or a second session in the same checkout isn't seen, and their runs still count. A run with no duration of its server's own, read at its notification after it ended in the background, counts another worktree's run that started meanwhile as overlapping. Any overlap, however short, keeps the whole run out. A scope whose runs all overlap gets no newer time, so its usual time ages out as one no run has updated. A CLI that can't answer stores the time, as before the check.

## Test progress in a run's log

Read October 31, 2026, in the test bed's raw captures (v0.8.8 to v0.8.17: MobileBuildMCP 2.7.1, Xcode 27.2, iOS 27.2).

- **A serial XCTest run** writes `Test Case '-[FeatureTests.ProbeTests testFails]' started.`, then `… failed (0.006 seconds).`, `passed (…)` or `skipped (…)`, with a capital C and no `on 'Clone …'`, unlike the parallel runner's `Test case '…' passed on 'Clone 1 of …'`.
- **An expected failure is written as passed.** `XCTExpectFailure` gives `Expected failure in -[FeatureTests.ProbeTests testExpectedFailure]: …` inside the case, then `Test Case '-[…testExpectedFailure]' passed`. MobileBuildMCP's counts for that run are 1 passed, 2 failed, 1 skipped: four of the five cases, the expected failure left out. So the count of a run's progress leaves it out too, and a finished run's count is the total the next run measures against.
- **`Testing started` is written only after the tests.** It's the last line of every finished 2.7.1 log captured, after `** TEST EXECUTE … **`. In the test bed's run copied ten times, a second apart, while it ran (v0.8.9, raw/shapes-midrun.log), the tests had started by the seventh copy, `Test Suite 'All tests' started at` at line 495 and `◇ Test run started.` at 498, and no copy held `Testing started` or `** TEST EXECUTE`. So progress is counted from xcodebuild's own start of testing, whichever of those comes first, and from the marker only when neither is there.
- **The tests' build ends before a second xcodebuild runs them.** MobileBuildMCP builds with `build-for-testing`, then runs `test-without-building`. In every test log captured (v0.8.10: raw/serial.log, swift-testing.log, profile.log, shapes.log), `** TEST BUILD SUCCEEDED **` is followed by that second `Command line invocation:`, `Writing result bundle at path:`, then the start of testing. A build's log (concurrency/build_sim.log) holds no such line; it ends `** BUILD SUCCEEDED **`. So from that line until testing starts, the phase is testing with no count, rather than the build's last step.
- **Swift Testing's lines** (v0.8.9, raw/shapes.log): `✔ Test passes() passed after 0.001 seconds.`, `✘ Test fails() failed after 0.006 seconds with 1 issue.`, `➜ Test skipped() skipped: "skipped on purpose"`, `━ Test knownIssue() passed after 0.001 seconds with 1 known issue.`, `✔ Test parameterised(value:) with 3 test cases passed after …` (once for its three cases), and a suite's `✘ Suite ShapesTests failed after …`. Some start with a zero-width space before the symbol. MobileBuildMCP counts that run's six tests as 1 failed, 3 passed, 1 skipped: the parameterised test once, the known issue's pass in none. Progress counts the same, leaving out the suite's line and the run's `Test run with 6 tests in 1 suite …`.
- **Read with string checks, not regular expressions.** The band read a run's whole test output once a second before 0.13.0, and each look still counts every line written since the last. Built with `swiftc -O` on macOS 27.2, the count took 23.6 s with Swift regular expressions on a serial log of 20,000 tests (60,000 lines, 3.7 MB), and 0.17 s with string checks.
- **Each tick reads on from the last.** `xcrew phase` is a new process each second, so what it has read of a log is kept in xcrew's cache (`phases/`, one small file a log): the byte offset through the last whole line, the start of testing, the tests counted and seen, and the latest step. The next tick reads only what was written since. A log shorter than what was read, or another file at its path (by its file number), is read afresh. A reading depends only on the log's bytes before its offset, so two readers sharing it, the band and another checkout's line, read as one: a slower one saving an older reading last only makes the next tick read some lines again. A reading nobody has kept for a day goes when another log's is first kept. Read in pieces, every test bed log came to the phase that reading it whole gives, at every piece, and the CLI tests pin that. On November 2, 2026 (macOS 27.2, APFS, release builds), on a 31 MB log a tick took 10–13 ms where reading the whole log took 31–50 ms. The first read of a log already that long takes 134–200 ms once. A run's first tick usually meets a log of a few kilobytes.
- **A run that tests a case more than once writes each run of it** (test bed v0.8.17, raw/retry, configurations, shapes-iterations, and field/probes.log). MobileBuildMCP's count is its result bundle summary's top level, which counts a test once however often it ran (`utils/xcresult-test-failures.js`, `extractTestSummaryCountsFromXcresult`, MobileBuildMCP 2.7.1).
  - `-test-iterations 5` (field/probes) starts each pass with its own `Test Suite 'Selected tests' started` and writes every test again: 20 results against MobileBuildMCP's 4.
  - `-retry-tests-on-failure -test-iterations 3` (raw/retry) stays in one pass and writes a failed test again at once: `testFails` failed three times in a row, `testFlaky` failed and then passed. MobileBuildMCP counts 1 failed, 2 passed, 1 skipped, the flaky test by its last try, yet its text and `structuredContent` still list `testFlaky` among the failures. The bundle's test list counts it `Passed`, its first try's failure only in its repetitions, so xcrew's report lists only the tests the list doesn't count passed, and its summary names the first of those. A test of one id that failed in another target stays listed.
  - A test plan's two configurations (raw/configurations) each start with `Test Suite 'All tests' started`. MobileBuildMCP counts each test once: 1 failed, 1 passed, 1 skipped.
  - Swift Testing's `-test-iterations 2` (raw/shapes-iterations) writes one `◇ Test run started.` and each test once, its time the iterations' together. MobileBuildMCP counts 5, as for one pass.
  - Swift Testing through a test plan's two configurations (raw/shapes-configurations, test bed v0.8.23, November 2, 2026) writes each configuration's run whole: its own `◇ Test run started.`, every result again, and its own `✘ Test run with 6 tests in 1 suite failed after …`, naming neither configuration. MobileBuildMCP counts 5, as for one pass. A Swift Testing name carries no suite, so a name written twice tells nothing, but a result after a run's total is another pass's: from there the line says `testing`, with no count.
- **What a tick costs.** The band asks `xcrew phase` once a second while a run goes, and each ask reads on from the reading kept for the log, then writes it back. The reading keeps the scheme the log's invocation names and its latest verdict as it reads them, the verdict from a line still being written or indented too, so a tick reads nothing again from the log's start or end; the line about other worktrees' runs reads their verdicts the same way, not from each log's last megabyte. It keeps the tests whose result it has read too, which is how a test written again is seen. The crash capture (raw/system-failure-crash) starts a second pass after the test host's crash with no test written twice, so a pass's start alone can't say a run is repeated, and the names stay. Each is kept as its name's 64-bit FNV-1a hash, not the name. Measured on November 2, 2026 (M1 Max, macOS 27.2, a synthetic log of 5,000 XCTest results of names about 85 characters long, one tick per 500): the kept reading went from 409 KB to 102 KB at 5,000 tests, and a tick from 30 ms to 20 ms, the process's start included. It still grows by a number a test, about 20 bytes.

  So progress counts through a run's first pass. From an XCTest case's result written a second time, the phase is testing, with no count: the log doesn't say how many more times a test will run, so no count of it can be held to MobileBuildMCP's. A start of testing written again is no sign of that, since a relaunch after a crash writes it within one pass (raw/timing.log, `Test Suite 'Selected tests' started` twice over one pass). Nor is a Swift Testing name, which carries no suite, so two suites' tests of one name are two tests. A Swift Testing run through a test plan's configurations can count past its total, which the phase then shows as `testing · N done`.
- **A cancelled Swift Testing test is counted as skipped, as MobileBuildMCP does** (v0.8.17, raw/cancel): `➜ Test cancels() was cancelled after 0.001 seconds: "cancelled on purpose"`, and MobileBuildMCP's 1 passed, 0 failed, 1 skipped. Progress counts it as a finished test.
- **Not read yet:** the parallel runner's live log, which no published capture holds.

## Stopping a program

Measured October 31, 2026, on macOS 27.2 with Xcode 27.2's Foundation, in a scratch program; nothing of a project's ran.

- **`Process` starts its child in a process group of its own, and `terminate()` stops the group.** `/bin/sh -c 'sleep … & wait'` run through `Process` was its group's leader (its pgid its pid), and its background `sleep` shared that group. After `terminate()`, the `sleep` was gone too, while `kill -TERM` of the same shell from a terminal left it running. So a background child of the program usually ends with it. One that ignores SIGTERM, or leaves the group, outlives it and can hold the program's pipes for as long as it lives: that's the case the runner's grace after a stop is for, and the case its test starts (`(trap '' TERM; exec sleep …) & wait`).
- **The runner signals the group itself, and the CLI stops what it started (November 3, 2026).** Foundation's docs don't say `terminate()` reaches the group, so a cancelled run sends SIGTERM to the program's group (`kill(-pid, SIGTERM)`); its test, a shell with a background child, goes red when only the program is signalled. The CLI watches SIGTERM and SIGINT (`Interruption`) and cancels its work on either, so a stop from Claude Code or a Ctrl-C ends the programs it started too, and it exits 128 plus the signal. A second signal while the work goes on ends the process at once, for work that doesn't stop when cancelled. A signal handled once the work has returned stops nothing; one handled as the work returns still counts as its stop, as nothing tells the two apart.

## Timing an awaited call in a test

Measured October 31, 2026: CI's macOS runner, from a run's logs, and this repository's own suite on a 10-core Mac, macOS 27.2, Xcode 27.2.

- **An awaited call resumes only when the cooperative thread pool has a thread free.** On CI's macOS runner, the runner's timeout tests measured 11.8-13 s around a call with a 200 ms timeout, and ended each time within a second or two of the whole suite. On a 10-core Mac, with the pool pinned to one thread (`LIBDISPATCH_COOPERATIVE_POOL_STRICT=1`), the same calls took 1.8-2.7 s and ended within a second of the suite's end, against 0.24 s with the pool's usual width. So a test that times an awaited call measures the suite's load as much as the call, and a test asserts what a stop guarantees instead.
- **So no test asserts elapsed time, and none waits on a sleep (November 2, 2026).** A test waits on the event itself: a line a process wrote, a file a build made, a process waiting on a lock (`pgrep` finds its `lockf`), a FIFO a stand-in build reads before it goes on. Code that waits on time takes a clock, and its tests move a `ManualClock`, whose sleeps resume only as the test advances it, or end when their task is cancelled. A wait polls its condition often and ends on a second condition when the code under test went wrong, so a broken build fails at once; it waits until one holds, and no test gives up on time (*No budgets*). The canary's scripts wait on the server's own log and replies, and stop it once it has answered: MobileBuildMCP 2.7.1 didn't exit when its input closed.
- **Nor does a fixture lean on the real clock (November 3, 2026).** CI's oldest-toolchain job, on a loaded runner, ran the pin check's tests 24 to 37 s after their fixtures were made. The fixtures dated the launcher's record by the real clock, 5 s back, and the check measured the server's 30 s age from its own now, so past about 25 s the record read as older than the server: five tests failed with "it started before the pin applied", none of them a fault of the check, which reads the machine's clock. Dating the record 26 s further back gave the same five failures on a Mac with nothing else running. A fixture now gives its dates and the machine's clock one moment. A stand-in for a program that runs on reads a FIFO no one writes (`HeldReader`) where it slept 30 s, which a run that slow outlived.

## Toolchains

On October 29, 2026, Swift 6.4.2 (Xcode 27.2 beta 3) on a contributor's Mac accepted a task-group closure that captured a local `Mutex`. CI's Swift job, on the newest Xcode of the `macos-26` runner, rejected it as a `sending` closure that risks a data race. The two compilers don't agree on every concurrency check, so a change that builds locally can still fail CI, and CI's answer is the one that counts. The `macos-26` runner image (version 20261013.0424.1) carries Xcode 26.0.1 to 26.6, and Apple's [Xcode system requirements](https://developer.apple.com/xcode/system-requirements/) put Swift 6.2 in Xcode 26.0 and 26.0.1, 6.2.1 to 6.2.3 in 26.1 to 26.3, and 6.3 in 26.4.1 to 26.6. So CI's newest toolchain was Swift 6.3, older than the contributor's 6.4.2. Each Swift job now prints its toolchain, and a floor job builds and tests on the oldest Xcode whose Swift is the version `Package.swift`'s `swift-tools-version` names.

The first run builds the CLI. The shim used to say "about 10 s" with no measurement behind it. Two cold first builds, `bin/xcrew --version` with an empty Xcrew cache, both on October 29, 2026, under Swift 6.4.2 (Xcode 27.2 beta 3): a fresh Mac took 15.4 s wall clock (`swift build` reported 11.5 s); a contributor's M1 Max (macOS 27.0.1, APFS, Swift's own caches warm) took 13.5 to 14.4 s over three runs (12.0 to 12.4 s). The shim states a range both support, and the README repeats it.

**Building after a reload.** After `/plugin` updates xcrew and `/reload-plugins` loads it, no SessionStart command hook runs. The mod's `session.start` fires, on a Claude Team org too, where a user-tier mod's `classic.*` and `prompt.*` hooks are skipped, and it starts the shim on its cheapest command, `--binary-path`, through `$.process.spawn`, not waited on and under no time limit: it lives until the module reloads, longer than a build takes, and is the one thing that builds. A call on the CLI asks the shim which build to run, `--binary-path`, spawned and read to its end: the shim names the build there, or builds it, or waits through its lock for the build another caller started, however long it takes, so no call is cut while the CLI builds and none starts a second build. A build that failed is remembered for 30 s with the compiler's reason, and a call in that time says it rather than build again through the shim. Before, the session start's own calls on the CLI built under the first caller's limit, as short as 10 s, which a 13.5 to 15.4 s build could pass, stopping it. The shim builds under `lockf(1)`, read in its man page on macOS 27.2: "BSD-style locking is used, as described in flock(2); the mere existence of the file is not considered to constitute a lock", "By default, lockf waits indefinitely to acquire the lock", and "In no event will lockf break a lock that is held by another process". The kernel lets the lock go when its holder ends, however it ends, so no waiter decides a holder is gone: a lock that named its holder's process id and start time, as `ps` printed it, read a live holder as gone under another language, and two waiters could each clear a dead one and build at once. A build that fails while others wait on it is said to them from `<key>.failed`, and not run again by each in turn; a run that starts after it builds again. A build outlives the caller that started it (November 3, 2026): in a check of 0.15.0, a session that ended while the build its start had begun was still running lost that build after it finished compiling and before the binary was put in place, and left its `<key>.output-<pid>` behind. The build had finished, so what stopped it came after: the shim wrote the build's output to the caller, who had gone, and that failed write ended it under `set -e`, before the copy. A test whose reader goes, with a build that prints as `swift build` does, loses the build the same way on the old shim. A closed terminal's hangup to the shim's group stopped the build too, mid-compile, in a test of that. So the lock's holder and the build run with hangups and broken pipes ignored, set in a subshell so the shim itself keeps its own; the binary is put in place before the build's output is written, and a write that fails stops nothing. A stop of the whole group still ends the build: by SIGTERM it leaves nothing behind, and by SIGKILL what it left goes with the next build. A build stopped outright, by SIGTERM or Ctrl-C, removes its output and the binary not yet in place, and the next build, under the lock, removes what one stopped harder left: a stale `.partial` kept its old file mode when the next build copied over it, so the CLI that landed couldn't run. `ci.yml release-build` times the release build on each push to main, as evidence.

## The branch's test runs

The evidence block's changed-line coverage counts a changed line as run when any of the checkout's test runs that can speak for its file ran it, and names those runs by when they finished. A run that ran no test, none counted or every one skipped, is left out: its coverage holds nothing run. Two runs may spell a file differently, as their builds were started; the merge takes each file once, as the file system spells it.

- **Which runs speak for a file.** A run speaks for a changed file only when the file hasn't changed since the run started: then the run compiled the file as it is now. A run starts when MobileBuildMCP names its bundle, from the time in the name: MobileBuildMCP 2.7.1 names it before the build for testing starts (`utils/test-common.js`, `createDefaultResultBundlePath`), while `xcodebuild` makes the folder only in the test phase, after compiling, so the folder's own date would let an edit made during the build pass as compiled. A bundle not named that way gives no start, and its run doesn't speak; nor does a run for a file whose date can't be read. With no changed file's date to go by, as on a branch that only deletes files, no run is read and the block says nothing of coverage. A run that compiled other content would mark the wrong lines, as when a commit since moved them, or when another branch's run was written in the same checkout. Leaving a run out only makes the block shorter; counting one wrongly makes it wrong. A switch of branch rewrites just the files that differ and gives each the time of the switch. Probed on November 2, 2026 (git 2.56.0, APFS, macOS 27.2): in a repository whose two branches differ in one file and share another, both dated 2026-01-01, switching branches dated the differing file to the moment of the switch, both ways, and left the shared one's date alone. So the rule needs no record of which branch was checked out when. Git's documentation doesn't state how a checkout dates files.
- **Its limits.** A file the same on two branches whose callers differ keeps its date across a switch, so another branch's run counts for it. The same holds within one branch across commits, and it's the rule's known limit. A tool that writes a file and keeps an older date (`cp -p`, `touch -r`, `rsync -a`, unpacking an archive) can make a run look current for content it never compiled. None of them is how source is edited or checked out in normal use.
- **The files no run speaks for** are named as changed since every run that covered them, neither run nor not run. When every run in the workspace started before every changed file's last change, the block says no run speaks for the changed lines. Runs that started before the earliest change are never read, since they can speak for no file. A run that covered a changed file whose changed lines can't run still speaks for it, so an older run's lines there don't make it one no run covered.
- **Every run read.** The evidence reads every run that can speak for a changed file, newest first, to its end (*No budgets*). The project's targets, read to leave out the files only test targets build, are read once, at the start and beside the runs. On the test bed's projects it took 12 to 19 ms, the CLI's whole start included (`xcrew graph --owner`, ten runs each, November 2, 2026); a large app wasn't measured. One failed test's images exported in 0.046 to 0.053 s (*The cost of an unfiltered export*), read beside the runs for every failed test, and the build log and the branch's diff are read once. On this Mac (M1 Max, macOS 27.2, Xcode 27.2, November 2, 2026), `xccov view --report --json` took 0.67 to 0.73 s on 19 of the 20 MobileBuildMCP bundles with coverage and 1.69 s on the other; each `xccov view --archive --file` took 0.63 to 0.64 s, four at a time; `xcresulttool get content-availability` about 0.02 s; `xcresulttool get test-results summary`, read first to leave out a run of no test, 0.05 to 0.06 s on 20 of them. So a run with eight changed files in its coverage reads in about 3 s, and ten such runs, read one after another, in about 30 s.
- **One pool for the reading.** Each `xccov` call costs about 0.7 s, most of it its own start, and about 100 MB, and the calls run well side by side: on this Mac's 8 performance cores, one call took 700 ms, 4 at once 787 ms and 8 at once 955 ms. So the runs are read side by side, and every command the evidence, or a run's report, starts goes through one pool (`CommandPool`) sized to the Mac's performance cores (`sysctl -n hw.perflevel0.physicalcpu`, else `hw.activecpu`, asked when the first command comes, so a report that starts none asks nothing; `sysctl` took 2.5 ms, median of 30). It replaces a fixed four files at a time. Each run reads in a lane of its own, the newest in the first, and a waiting command goes by its lane before its turn, so the newest runs' commands go ahead and the runs finish roughly newest first: a run's first reads hold one slot each, so older runs fill the rest meanwhile, and the newest are read whole first. With no lanes every run's commands would take turns and finish near the end together. No run, and no command, has a limit (*No budgets*). A command cancelled while it waits leaves the queue at once.
- **What the pool saves.** Measured on November 2, 2026 (the same Mac, macOS 27.2, APFS, Xcode 27.2), the reading's commands for a run of ten changed files, replayed in process through the system's runner: per run, the summary, content availability, the file list and ten file reads, on one bundle of a small macOS package read again for every run, so its files were cached after the first. One run took 2.96 s one after another and 2.33 s through the pool; five runs 14.85 s and 6.95 s; ten runs 29.68 s and 12.47 s (medians of five, a pool of 8, measured before the pool had lanes, which change the order the commands run in, not how many run at once). A run's first three reads still go one after another, which bounds one run's time. `xcrew evidence` itself on a branch of ten changed files wasn't timed: no bundle on this Mac covers ten files, and a package built here gave none for its library's files, so that waits for a test run with coverage of that size. Those are a small project's bundles: a large app's report lists thousands of files and was not measured, so how many of its runs fit in the 120 s isn't known; those that don't are left out and counted. xcrew's own work on top, timed on the test bed's coverage capture replayed, is about 0.02 s for one run or two.

## Commands that remove the person's data

A text xcrew tells Claude that gives a command removing or overwriting something of the person's says what's lost and that it's the person's to agree to, right before the command, which ends the text, so nothing of the sentence around it is copied into it. The routing rules' harm guard has DerivedData deleted only when the person asks; the same holds for their folders, builds, simulators, tools and settings. The commands checked for, as `ManifestTests` matches them in every text it lists as told to Claude:

- `rm` with a recursive flag, in any order of flags (`rm -r`, `rm -rf`, `rm -fr`, `rm -R`);
- `kill`, `killall`, `pkill`;
- `simctl delete`, `simctl erase`;
- `xcodes uninstall`, `brew uninstall`, `npm uninstall`;
- `defaults write`, `defaults delete`;
- `--delete` (MobileBuildMCP's purge), and `xcode-skills --force`, which replaces with no copy kept; `setup --force` keeps a backup and isn't one.

The sweep of November 2, 2026 found and gave the condition to the module cache's `rm -rf`, a held build database's `kill`, the leftover `.xcodebuildmcp/` folder's `rm -r`, the three `simctl delete` offers, `xcrew space`'s purge note and `xcodes uninstall`, the doctor's `brew uninstall` and `npm uninstall` of the old XcodeBuildMCP, the unsigned-agents `defaults write`, and `xcode-skills --force`, which deletes the project's own skills. It left as they are: `setup --force`, which keeps a backup of what it replaces; the purge's and the runtimes' `--dry-run` commands, which delete nothing (the purge note, which says how to delete, carries the condition, and the DerivedData line says deleting it costs a cold build and is the person's call); `context/routing.md`'s routing of `erase_sims` to MobileBuildMCP, which routes rather than offers; the reference skill's `clean`, which the routing rules allow; `echo <version> > .xcode-version`, offered only where no pin file is; the README, which the person reads, not Claude. A command added with a pattern not here has no test holding it: add its pattern here and to the test.

## Tried and rejected

| Option | Why not |
| --- | --- |
| MobileBuildMCP's `incrementalBuildsEnabled` | Slower than plain rebuilds in testing, downloads and runs `xcodemake`, and writes a large `Makefile` into the project root |
| Building through the Xcode MCP by default | Shares and fights Xcode's DerivedData, and follows the person's active scheme |
| Python for Xcrew's logic | Apple's Python is 3.9 and contributors to an iOS tool write Swift; a cached Swift binary also starts faster (about 0.02 s against 0.05 s) |
| Swift scripts | Compiled on every run, about 0.65 s per call, too slow for hooks |
| A shell installer as a third install path | The plugin already installs without mcs, and a third path would drift |
| Counting modules for the build gauge | Nearly every module has a task early in a build, and none says when it's done; see *Build and test progress* |
| Adding expected failures to MobileBuildMCP's counts | The counts are MobileBuildMCP's own, and a result that disagrees with the server's summary line is harder to trust than one beside a note. xcodebuild's log and the bundle's total do count them, though (*Known issues and expected failures*), so this rests on MobileBuildMCP's line alone. Claude gets the true total from Xcrew's note either way |
| `swift-subprocess` | A package dependency means a network fetch on every user's first build |
| Routing build and test tools from their descriptions (`tool.describe`) | Read on October 29, 2026: "Only tool names and server instructions load at session start" ([MCP](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search)), and the mod API's `tool.describe` fires "at the moment the engine first renders the tool's schema for the model", which for a deferred MCP tool is when ToolSearch loads it. Claude picks the server from names before any description arrives, so a routing line there comes after the choice and can't replace the session briefing |
| Loading MobileBuildMCP's tools up front (`alwaysLoad`) | Claude Code allows it: "set `alwaysLoad` to `true` in that server's configuration … The `alwaysLoad` field is available on all server types" ([MCP](https://code.claude.com/docs/en/mcp)). But MobileBuildMCP 2.7.1's `tools/list` came to 52 tools and 314,229 characters (about 78,000 tokens), mostly input schemas, and "startup [would] wait for the server's tools, capped at the standard 5-second connect timeout". A ToolSearch round trip costs far less. Per-tool `anthropic/alwaysLoad` in a tool's `_meta` is the right granularity, and it's open to whoever owns the server. |
